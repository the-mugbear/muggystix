# BlueStick Scripts

This directory contains utility scripts for deployment and maintenance.

## Scripts Overview

### Deployment Scripts

- **`deploy.sh`** - **Main deployment script**; interactive menu with seven options:
  1. Start / Rebuild — **the upgrade path for an existing instance; run it with the stack up** (a new host uses option 2). In order:
     - **The rollback point.** Snapshots the running images as `bluestick-rollback-<service>:previous` and takes a pre-deploy backup (database **and** `uploads/`; it aborts if either cannot be written — `BACKUP_ALLOW_MISSING_UPLOADS=1` accepts a database-only backup, `DEPLOY_WITHOUT_BACKUP=1` none at all), recording the dump and its schema revision in `.deploy-rollback-state`. **After a deploy that did not finish healthy it keeps the existing rollback point instead** and says so — a new snapshot would capture the failed build, a new dump the migrated database. (Exceptions, each stated when it applies: the database is still at the pre-deploy schema → a fresh dump is taken and recorded; the earlier deploy was finished by hand and is healthy → a new rollback point; `DEPLOY_NEW_SNAPSHOT=1` forces one.)
     - **Images.** Stops, with nothing built, when the database image is not on the host and cannot be pulled. Lists the pinned base images the host lacks and whether the registry answers — the build pulls them, and downloads packages for every uncached layer.
     - **Build.** A failed build stops here, the old containers still running.
     - **Staged start.** Stops the two workers, starts the database and **the backend alone**, and **waits for the backend** — up to `DEPLOY_HEALTH_TIMEOUT` seconds (default 1800), printing progress and whether a schema migration is running; then starts the workers, then the frontend. The backend goes first so that ONE process migrates the schema with nothing else connected: every process migrates at start under the migration lock, and a worker started beside it would either be the one that migrates or sit waiting. (This release's revisions build their indexes inside the upgrade transaction, not `CONCURRENTLY`.)
     - **"Healthy" means the new build.** The backend container's image is compared with the one just built: if `up` failed before recreating it, the script says the previous build is still running, starts its workers again and exits non-zero — it does not report the old build as a successful deploy. A failed later `up` is reported too, never a silent exit.
     - It tells the two failures apart: the backend container **exited or keeps restarting** → the boot migration failed, roll back with option 7; the backend is **still running at the timeout** → it has not crashed (a long migration holds the migration lock) — do **not** roll back, follow the logs and finish with `docker compose up -d`.
     - After a healthy start it removes **this project's** untagged images (by the `com.docker.compose.project` label — not every dangling image on the host) and Docker build cache older than 7 days (host-wide by nature; `DEPLOY_PRUNE_BUILD_CACHE=0` skips it), then lists the data repairs this instance has not run (see `data_repairs.py`) — or says it could not check.
     - **It must run from the folder the stack was started from.** Compose names the project, and the database volume `<folder>_postgres_data`, after the folder (unless `COMPOSE_PROJECT_NAME` pins it), so the new source of an upgrade goes in a new folder with the SAME name and path as the old one. When this folder's project has no containers but BlueStick runs on the host under another project, options 1 and 2 stop before changing anything, naming the folder that stack was started from. If that folder still holds a tree, run the script there; if it is gone, put the new source at its path. The alternative is to pin `COMPOSE_PROJECT_NAME`. Otherwise option 1 would back up nothing and start a second stack on a new, EMPTY database. `DEPLOY_SECOND_STACK=1` is for a host that runs two on purpose. `backup-db.sh`, `status.sh` and option 5 report the same condition.
     - It refuses a `.env` left behind by an interrupted option 4 (`SECRET_KEY=teardown`). A prompt that meets end of input (a piped run) takes its stated default or stops with a message; it never ends the script silently.
  2. First-time setup (generate `.env` + SSL certs + build + start) — where a new host starts. It builds, then uses the same staged start as option 1 (backend alone, wait, workers, frontend); a failed build, a backend that does not stay up or a failed later `up` ends with a message and a non-zero exit, never with "First-time setup complete"
  3. Reconfigure IP address
  4. Nuclear clean — destroys **this Compose project's** containers, database volume, networks and built images (selected only by the `com.docker.compose.project=<name>` label, so another copy of the tree on the same host is never touched) and this folder's `.env`. Before anything is removed it saves `.env` + `ssl/` the way option 6 does (the dump's encrypted secrets need the key in `.env`) and runs `backup-db.sh`; if either fails — a failed copy of `.env` included — it stops and asks for a second typed confirmation (`DELETE WITHOUT BACKUP`). The temporary `.env` it writes when there is none (so Compose can parse the file) is removed on every way out, an abort included. Base images, Docker's build cache, `./uploads` and `./ssl` are left
  5. Security status check — the database's TLS and whether its port is published, one sentence on what `uploads/` is (the containers' folder, mode 700, which your account cannot list — that is the correct state, and the line says how to look inside through the container), and the ownership and permission findings below, without asking anything

  **Run it as one ordinary account that can use Docker (a member of the `docker` group), the same one every time — not as root and not with `sudo`.** Nothing in it needs root, and a run as root leaves `.env`, `ssl/` and the backups root's, so the next ordinary run cannot renew the certificate, back up the key or rewrite `.env`. Options 1–3 check this before they write anything: `.env` and the TLS key readable by other accounts, `.env` or `ssl/` owned by another account, `uploads/` owned by anyone but the containers' user (UID 999) or you, and the script itself running as root. Each finding is printed with the one command that fixes it; what your account can fix itself (a file mode) is offered as **f**, and otherwise you **c**ontinue or **s**top. It never runs `sudo` and never waits on a password; with no one at the keyboard it says what it found and goes on. `uploads/` needs nothing from you: the script only makes the folder, and the backend takes it over when it starts (it makes every sub-folder, gives the tree to UID 999 and sets it to 700). An `uploads/` that is still another account's AFTER a start means Docker could not change its owner there (rootless Docker, an NFS share with `root_squash`, SELinux); the backend log's `[entrypoint]` lines say why.
  6. Back up `.env` + SSL to the parent folder (before a re-copy deploy); "Backed up" is printed only for a copy that succeeded
  7. Roll back to the previous build. In order: re-points the image names at the `:previous` snapshot; **stops the application** (the database stays up); compares the database's schema revision with the one recorded at the pre-deploy backup. Unchanged → no restore. Changed, or not determinable → it says the failed deploy migrated the database and restores the pre-deploy dump by running `restore-db.sh` (asks first, default yes); declining leaves the instance stopped unless you type `START ANYWAY`. Then the same staged start as option 1, with `--no-build`, and a closing line with the state the instance is in (`RUNNING`, `STOPPED`, `NOT RUNNING`, `STILL STARTING`, `PARTLY UP`) and the next step. By hand, if it cannot finish: `./scripts/restore-db.sh <PREDEPLOY_DB_DUMP from .deploy-rollback-state>`
- **`stack-lib.sh`** - Not run by hand (it is sourced): the functions `deploy.sh`, `restore-db.sh`, `backup-db.sh`, `status.sh` and `collect-logs.sh` share — `compose_project_name` and the stack-identity check (is BlueStick running under another Compose project?), the staged start (backend alone, wait, workers, frontend), the backend wait that tells "still migrating" from "crashed", and `ask`, the prompt that states what happens at end of input. Also `print_tunable_settings`, the **settings readout** that ends option 1 and option 2 and is part of `status.sh`: the settings an operator is most often told to change after a look at a host's logs (container memory, PostgreSQL sizing, API pool and timeouts, import and report limits, log rotation, backups), each with the value in force and its source — `.env`, the shell's `environment`, or `default`. Defaults are read from where they are defined (`${NAME:-default}` in `docker-compose.yml` or a script, else the commented `# NAME=value` line of `.env.example`), so the readout cannot drift from them; no secret is ever on the list. To change one, set it in `.env` and run option 1 again.
- **`upgrade-instance.sh`** - Upgrade a file-copy deployment (no git on the host). Precondition, done by hand first: rename the running instance's folder to `<name>_backup_<date>`, copy the new source tree next to it and rename it to the **original** folder name (docker compose keys the database volume on the folder name — `<name>_postgres_data`). Then, from the new folder, `./scripts/upgrade-instance.sh`: it verifies that volume exists (refuses otherwise, `--allow-fresh-db` to override), carries `.env`, `ssl/certs/*`, the uploads dir (moved; `--copy-uploads` to copy — since 2.495.2 that folder is the containers', so the move or copy runs in the database image on the folder both trees share, and only when the trees have different parents, or no image is on the host, does it stop with the one `sudo` command to run), a custom `NGINX_CONFIG`, `.deploy-rollback-state` and the report-template images each `template.json` declares (a logo…) across, reports `.env` keys the new `.env.example` adds and any top-level files only the old folder has, then runs `deploy.sh` option 1 and checks the API's reported version against `platform_version.json`. Idempotent: identical files are skipped, differing ones abort rather than overwrite. The exception is a CA-issued certificate already installed in the new folder (`ca/local-ca.sh install` before the upgrade): it is kept, and the old instance's certificate is not carried. `--no-deploy` stops before the deploy, `--from <dir>` names the old folder when auto-detection is ambiguous, `--yes` answers yes to every confirmation.

### Maintenance Scripts

- **`collect-logs.sh`** - Anonymised diagnostics bundle (container logs, ingestion queue, parser audit, agent feedback), safe to share once its feedback has been read. It also says which frontend build is actually being served (after a file copy with no rebuild the deployed files name a newer version than the browser gets), which agent routes were called in the last 30 days and how far back that log reaches (`agent_surface.txt` — route templates and counts only), and how many requests the browser cancelled (nginx status 499: a reader who moved on, not a failure). Safe to run during a boot migration: its queries give up after 5 seconds on a locked table instead of waiting, and the bundle records the database's live sessions and lock waits (for the live state alone, `migration-status.sh` is quicker). Options: `--since 72h`, `--terms FILE` (extra names to remove), `--no-feedback` and `--out DIR`. The bundle is written to the folder you ran the script from (or `--out DIR`); when your account cannot write there it goes to the project folder, else your home folder, and the closing line says where — it is never discarded (before 2.519.0 a folder it could not write in lost the whole bundle).
  - `feedback.txt` holds the agents' feedback **in full**: the newest 200 entries, with date, rating, prompt version, client and model, friction notes, endpoint critiques, tool suggestions and reviewer notes. It is scrubbed like every file, but it is free text by design, so a name the database never held can survive. The end of the run gives the count and asks you to read the file before moving the bundle. `--no-feedback` leaves it out.
  - `containers.txt` ends with how many OTHER Compose projects on the host run BlueStick, with their running containers and where each was started from relative to this folder (this folder, a sibling, inside it, a parent, elsewhere). It gives counts only, never a project or folder name. "This folder's project has 0 containers" beside another project means the bundle was collected from the wrong folder.
  - `permissions.txt` (2026-10-14) says who owns `.env`, `ssl/`, the certificate, the key and `uploads/` — as a class (this account, root, the containers' user, another account), never a name — with each mode; what `deploy.sh`'s ownership check would ask about, by kind; whether the bundle was collected as root and whether Docker is rootless or remaps user namespaces (the usual reason a container cannot take `uploads/` over); the database's TLS state and how many of its connections use it; and the `[entrypoint]` / `[db-tls]` lines of the containers' current logs, whatever `--since` says. Send it when a deploy stops on permissions.
  - `tls.txt` reports the certificate nginx actually serves: self-signed or CA-issued, expiry, SAN counts, whether it names `HOST_IP`, whether it is the file in `ssl/certs` and matches its key. It shows derived facts only, never names. The health checks use `curl -k`, so this file is the only place a certificate problem appears. The probe gives up after 10 s, and a refused or failed connection is recorded as the result; it never stops the collection.
  - `versions_and_schema.txt` says **what the last boot's migration did** — each `Running upgrade` line and the one line a failed or refused upgrade logs, taken from the backend's and the ingestion worker's whole current log whatever `--since` says — and the **counts the three refusing revisions check** (`b2e5a8c1d4f6` duplicate scanner findings; `e1b4c7d0a2f5` a scope with no project or an entry held by two scopes of one project; `a4f8c2e6b0d1` a CIDR twice in a scope with differing descriptions or sites). Counts only; each reads the same before and after its revision, and a query an older schema cannot answer says so and the collection carries on. `migration-failure-report.sh` prints the same counts.
  - `versions_and_schema.txt` also carries the **data-repair ledger** (repair names, mode, when, a row total — the table stores counts only, never a row value) and the Postgres memory settings with the two signals for changing them: the cache-hit ratio (`blks_hit` / `blks_read`) and temp-file volume (`temp_bytes`) since the last stats reset.
  - `agent_surface.txt` holds agent sessions, refused agent calls by route template, MCP tool outcomes and client handshakes, proposals by kind and status (with accept errors), evidence records (by outcome, with the size of their raw output), and feedback by prompt version. It holds counts only, because a refused call never leaves a traceback. MCP client names, and the tool names callers sent, are free text, so they are harvested (not client versions: a version names no one, and one shaped like a date erased that date from every log line). Names BlueStick's own source uses (such as `claude-code` or a catalogue tool) stay readable; anything else becomes a pseudonym.
  - `request_timing.txt` summarises the backend access log per method and route template: requests, p50 and p95 request time, mean `db_ms` (time inside database statements) and `db_n` (statement count), and the number of `SLOW request` lines — sorted by total time, the top 60 routes. Only the template is shown, never the path; a request that matched no route is counted under `(unmatched route)`, and a line whose method is not a real HTTP method is not counted (the method, like the path, is the client's text). Logs written by a build without those fields get one line saying so.
  - `sql_statements.txt` lists the 40 statements the database spent most time in, from `pg_stat_statements`: calls, total and mean milliseconds, rows, and the normalised text (constants are `$1`, `$2` …, so table and column names only), cut to 400 characters. Utility statements are left out, comments are removed, and any string literal that remains — `'…'`, `E'…'`, dollar-quoted — is replaced. The script runs `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` — the one thing it writes to the database. When the library is not preloaded (`shared_preload_libraries`, set in `docker-compose.yml`; a database container started before that needs recreating) or the role may not create the extension, the file holds one line saying why and the collection carries on.
- **`diag_summaries.py`** - Writes those two files for `collect-logs.sh` (stdlib only, host `python3`): `request-timing <backend log>` and `sql-statements` (rows on stdin). Not run by hand.
- **`scrub_logs.py`** - The scrubber `collect-logs.sh` runs over the bundle (stdlib only, host `python3`); it fails closed. A harvested value made only of digits and punctuation (a date, a time, a version) is never replaced, because it names no one and replacing it would blank that date or version throughout the logs. Secrets are the exception.
- **`parse-audit-agent-prompt.md`** - Bootstrap prompt for an agent auditing parse accuracy on the client network (what the operator provides, the report of redacted shapes it returns); the short version is `documentation/PARSE_AUDIT_BRIEF.md`.
- **`migration-status.sh`** - **Is a boot migration working, blocked, or restarting?** Read-only and safe to run while a migration is in progress (its own queries read only the system catalogs and `alembic_version`, and give up after 5 seconds on a lock). Shows the containers and their uptime, the revisions logged ("Running upgrade A -> B", and whether the upgrade has started over), the revision stamped in the database, every non-idle database session with how long its transaction and statement have run, and who waits on whom. One pid that stays the same between runs with a long `in_transaction` is the migration; it is working unless its `wait_event_type` is `Lock`. `--watch [SECONDS]` refreshes it. Never interrupt a running migration: the upgrade is one transaction, so a kill rolls it all back and the next start repeats it.
- **`migration-failure-report.sh`** - **A boot migration failed: collect what is needed to say why**, in one text file (`bluestick_migration_failure_<time>.txt`, mode 600, git-ignored). Read-only. The verdict the application stated (`NOTHING WAS CHANGED` = the upgrade rolled back, no restore needed; `schema left PARTWAY` = restore), the last traceback and PostgreSQL's own ERROR lines, how far the upgrade got and whether it started over, the stamped / pre-deploy / expected revisions, each container's restarts, exit code and `oom_killed` with its memory limit, disk space, database and table sizes, the server's timeouts, the count of issues with two scanner findings (the one revision that refuses on data), invalid indexes, and live sessions. SQL parameter values are removed and IPv4 addresses replaced, but it is **not** the anonymised bundle — read it before sending. Options: `--since 6h`, `--out FILE`.
- **`status.sh`** - Quick status check of the running instance: container health, the **newest backup and its age** (a warning when it is older than `BACKUP_WARN_DAYS`, default 7, or has no uploads archive), **when the TLS certificate expires** (read from `ssl/certs/networkmapper.crt`; a warning within `CERT_WARN_DAYS`, default 30, or once expired), and the **data repairs not yet applied** with the command for each, then the stack's containers and volumes and the free space on the folder's disk. It asks compose which containers are running, so it works whatever the folder (or `COMPOSE_PROJECT_NAME`) is called
- **`check.sh`** - **The gate** — one command, run before every push (there is no hosted CI): `./scripts/check.sh` or `make check`. (1) the backend suite in the **report-worker** image, with `report-templates/` mounted, which **fails if any test skipped for want of Quarto or the templates** — in the plain `backend` image those tests, the hostile-text contract among them, skip and the run is green; (2) `ruff check` over `backend/` in the same image (pyflakes rules only, `backend/ruff.toml`, `--no-cache`) — **any finding fails the gate**; (3) frontend `tsc --noEmit`, `npm run lint` (ESLint; a warning fails it) and `vitest run`; (4) `test-alembic-roundtrip.sh` (every downgrade, then `alembic check`). `--fast` skips (4); `--only backend|ruff|frontend|alembic` (or `CHECK_ONLY=`) runs one step and says it is not the gate. **Step (1) is sharded:** the test files are split into `CHECK_SHARDS` groups (default 4; capped at the machine's processors and at what the database's `max_connections` leaves free, 12 connections a shard) and each group runs at once in its own container against its own test database — no new package. Every test file is in exactly one shard (the plan is compared with a second listing of `backend/tests` before anything starts, and a difference fails the step); the step fails if any shard fails or ends without pytest's tally, the Quarto / template skip check reads every shard's log, and the summary line carries the summed counts with the wall time and the longest shard. Shards are balanced by seconds from `scripts/check-shard-weights.txt` (heaviest file first to the lightest shard; a file it does not name gets a default weight and still runs, so a new test file needs no edit there); `./scripts/check.sh --update-shard-weights` runs step (1) alone and rewrites that file from pytest's durations when the run passes — do it when the longest shard drifts well above the others. `CHECK_SHARDS=1` is the single process with live output. Every step runs even when one fails; a one-screen summary ends the run and the exit status is non-zero on any failure. It needs the stack up and the images built, builds and pulls nothing, and sets `BLUESTICK_SKIP_DB_INIT=1`, so it cannot migrate the development database. From a git worktree it runs the worktree's source in the main checkout's compose project (`CHECK_COMPOSE_ROOT` overrides). `CHECK_PYTEST_ARGS="-k name"` passes arguments to pytest, in every shard. Interrupted (Ctrl-C), it removes its log directory, every suite container of the run (`bluestick-check-<script pid>[-s<N>]`) and drops **its own run's** test databases (`<db>_test_<suite container's host>_<pid>`, one per shard, and the scratch databases the migration tests make beside them); a failed run keeps its logs and names the shard log to open. Databases left by runs killed some other way are swept at the start of any later suite run when they are more than a day old and have no connections (`backend/tests/conftest.py`)
- **`bump-version.py`** - Bump the backend and / or frontend version in every place it is written, on the host (stdlib Python): `./scripts/bump-version.py --backend minor`, `--frontend patch`, both at once, `--dry-run` to see what it would change. It writes `platform_version.json`, `frontend/package.json`, every `${APP_VERSION:-…}` / `${FRONTEND_VERSION:-…}` fallback in `docker-compose.yml` (the `BACKEND_VERSION` build arg included) and the two root `version` fields of `frontend/package-lock.json` — never a dependency's. It refuses and changes nothing when any of them already disagrees with `platform_version.json`. Then run `versionConsistency.test.ts` (it prints the command)
- **`seed_demo_data.py`** - Seed a realistic demo project (hosts, scopes, findings) so the Posture hub (Posture / Segments / Patterns / Evidence) and Findings are evaluable on a fresh install. Options: `--name`, `--hosts` (default 400), `--wipe` (delete an existing project of the same name first). Runs inside the backend container.
- **`seed_eval_scenarios.py`** - A SMALL project where every host is placed on purpose, each with an "open X, expect Y" check, for evaluating a feature by eye. `--wipe` deletes only its own project and rebuilds. Runs inside the backend container.
- **`seed_acceptance_fixtures.py`** - Build THE project MCP acceptance runs happen on (`documentation/MCP_ACCEPTANCE_QUESTIONS.md`): one nominated project named "Acceptance", dense on purpose. The first run builds it — the demo inventory (`seed_demo_data`, `--hosts`, default 400), the named-asset scenario (`seed_named_assets`), every hand-placed scenario (`seed_eval_scenarios`), one import per saved scanner file under `backend/tests/fixtures/native` through the real upload route (`nmap-tls-verbose.xml` is held back for the run to upload), and a placed import (`acceptance-placed.xml`: an IPv6 web host, SSH on 443, two guessed ports, an instruction-like banner). A later run tops it up; `--rebuild` deletes it and its companion and builds both again. No other project is touched. Then, through the real API routes: four role accounts (`acc-lead`, `acc-analyst`, `acc-auditor`, `acc-viewer`), a host note thread with an image and an agent's note written in Markdown, a finding comment thread with a report image, an issued client report, a NetExec import with uninterpreted lines, work that waits on the analyst (18 owned findings that need them — 10 to decide, 8 to write —, a host in review, an assigned test), a host test proposed by another person, and a second project ("Acceptance — other project", created as the first global admin) whose ids a cross-project request must be refused. Where the installation has remediation tracking on it adds four remediation records — one of them "Reported fixed", which puts its host into Retest pending; it never turns tracking on, and says so when it is off. Whether or not tracking is on, it marks one host of a finding nobody owns Retest pending through the people's endpoint route (2.501.0), so the project's retest list, its notification to every member and "Record retest…" have something to show. It also adds ONE installation-wide scanner integration, "[acceptance seed] scanner" (Nessus type, the documentation address `https://192.0.2.10:8834`, credentials that say they are fake), created as the first global admin through `POST /integrations/` — the one thing it writes outside the two projects; `--rebuild` leaves it, a re-run reuses it, and creating it contacts nothing (the connection test is never called). Prints admin / analyst / auditor / viewer agent keys and writes them, with the fixture ids and the accounts' passwords and TOTP secrets, to `uploads/acceptance-fixtures.json` (mode 0600). Idempotent: a re-run reuses the accounts, mints fresh keys and skips fixtures and imports already present. Runs inside the backend container; local development only. **Client-report content (2026-10-14):** eight findings with written report text — complete ones (one with a captioned table in its Evidence text and a placed image, one with an unplaced image printed after its note, one with a test result, an informational one whose only image is placed so it has no Evidence section), two missing one required section (one naming "Finding #12", so "Text the reader cannot follow" shows) and two missing two — found by title on a re-run; the report defaults' empty details (engagement type, distribution, application URLs) and the project's dates filled, an owner's edits kept; one draft, "Acceptance — walkthrough draft", that overrides the classification.
- **`seed_finding_owners.py`** - Give a project findings owned by SEVERAL people, so the Findings page's Owner filter can be seen listing teammates (a real deployment has many promoters; the demo seed has one owner). Makes three placeholder member accounts (`owner-ana`, `owner-ben`, `owner-cy` — random passwords that are not printed or kept, so nobody signs in as them), adds each as a project analyst, and hands them the project's UNOWNED findings in turn, leaving every third unowned; a finding that already has an owner is never touched. `--project ID` (required), `--dry-run`. Idempotent: once those accounts own a finding in the project a re-run hands out nothing more. Runs inside the backend container; local development only.
- **`seed_named_assets.py`** - Layer the named-asset scenario onto that demo project (imported-but-unresolved FQDNs, domain scope, a load balancer with four vhosts, a rotated address, per-vhost findings, host tests aimed at a name and tested bindings). Goes through the real write paths. `--reset` removes only the rows a previous run created (tracked in a per-run manifest under the uploads dir) and re-seeds. Neither seed is run by `deploy.sh` — they are dev/demo-only and always manual.
- **`generate-ssl-cert.sh`** / **`generate-ssl-cert-simple.sh`** - SSL certificate generators (also invoked by `deploy.sh` during first-time setup). They make a self-signed certificate; for one signed by your own root CA, see `ca/local-ca.sh` and [`ca/README.md`](../ca/README.md). `deploy.sh` option 3 (Reconfigure IP) regenerates a self-signed certificate but keeps a CA-issued one, and refuses (changing nothing) when a CA-issued certificate does not name the new address.
- **`permissions-lib.sh`** - Not run by hand (it is sourced): the one check of who owns `.env`, `ssl/` and `uploads/` and who can read `.env` and the TLS key. `deploy.sh` asks about its findings before it writes anything; `collect-logs.sh` writes the same findings into the bundle's `permissions.txt`.
- **`postgres/start-with-tls.sh`** - Not run by hand: it is the `db` container's entrypoint (compose mounts it). On every start it gives PostgreSQL the certificate in `ssl/certs` — copied to a folder only the `postgres` user reads, since that user cannot read a mode-600 key that is yours — and turns TLS on; a renewed certificate is picked up by restarting the database. A pair PostgreSQL would refuse (missing, not a certificate and its own key) starts the database **without** TLS (also over an `ssl = on` an earlier setup step left in the database's own settings) and says so on three `[db-tls]` lines in `docker compose logs db`; `deploy.sh` option 5 shows which it is. (It replaces `init-ssl.sh`, which ran once at initialisation as the wrong user, and `ensure-ssl.sh`, which only first-time setup ran.)
- **`rdap-lookup.py`** - Bulk RDAP lookup that writes a file you upload like any scanner output (the RDAP parser turns it into per-host registration attribution). Runs wherever you have connectivity, outside BlueStick on purpose — the server makes no network queries.

### Database Scripts

The schema is owned exclusively by **Alembic** — every backend container runs
`alembic upgrade head` on boot. There is no manual "create tables" step; never
run `Base.metadata.create_all` against a live database (it bypasses Alembic
version tracking).

- **`backup-db.sh`** - Back up the database: logical `pg_dump` (custom format), or a raw volume snapshot if Postgres is down. A logical dump carries the `pg_trgm` extension + all indexes. It also archives `uploads/` (evidence images, issued reports, screenshots) as `nm-uploads-<timestamp>.tar.gz`. Backups go to a sibling `<project>-db-backups` directory next to the project folder, so replacing the folder does not wipe them; override with `BACKUP_DIR=/path` (`deploy.sh` passes it on to its backups).
  - **A failure says why.** Each step's own message (pg_dump, pg_restore, tar, docker) is printed under it, with what that kind of error usually means (a full disk, a path an account cannot read or write, SELinux enforcing, a `POSTGRES_USER` / `POSTGRES_DB` the database does not have, no access to Docker). Before anything is dumped it checks that your account can run compose on the project (an `.env` it cannot read fails every compose call) and can create and write in the backup folder — a project in `/opt` whose parent only root can write cannot hold the default folder beside it; the message names the folder's owner and mode, and the command that fixes it.
  - **A running database that does not answer is not copied raw.** The volume snapshot is for a database container that is stopped or absent; one that is running but refuses connections (still starting) is reported and nothing is taken (`--volume` forces a snapshot).
  - **Success means read to the end.** The dump is converted back to SQL and discarded (`pg_restore -f /dev/null`, inside the `db` container), which decompresses and parses every data block; each tar archive is listed to its end. Listing a dump (`pg_restore --list`) is **not** that check: the table of contents is written at the front of the file, so a dump cut to half its size still lists every entry. The `.meta` beside the backup records how it was verified, plus `bytes=` and `sha256=` of the dump (or snapshot) and `uploads_bytes=` / `uploads_sha256=` of the uploads archive, for `restore-db.sh` to compare.
  - **A failed uploads archive is a failed backup** (exit 1, the database artifact kept): the dump alone restores rows that point at files which are gone. `--allow-missing-uploads` (or `BACKUP_ALLOW_MISSING_UPLOADS=1`) accepts a database-only backup; `deploy.sh`'s pre-deploy gate honours the same variable.
  - **Private files.** `umask 077`; the backup directory is set to mode 700 and every artifact to 0600, owned by the user who ran the script — the archives are streamed out of the helper container and written by the shell, so nothing is root-owned and no `sudo` is needed. (Archives made before this are root-owned and world-readable inside a directory that is now 700; retention removes them as they age out.)
  - **No image to pull.** `tar` runs in the database's own image (the `db` container's, else the one `docker-compose.yml` names), never `alpine`.
  - **Retention.** After a successful backup the newest `BACKUP_KEEP` backups are kept (default 10; `0` keeps all), each with its `.meta` and uploads archive; what was pruned and the free space left are printed. Never pruned: the backup just made, and the pre-deploy dump option 7 would restore. A **backlog** — more than `BACKUP_PRUNE_MAX` (default 3) to delete in one run, as on the first run over a directory that was never pruned — is reported and **not** deleted; `BACKUP_PRUNE_BACKLOG=1 ./scripts/backup-db.sh` deletes it once, deliberately.
- **`restore-db.sh`** - Restore a `backup-db.sh` artifact — the database and its matching `uploads/` archive.
  - **The backup is verified first, with the current database untouched.** Its size and SHA-256 are compared with the `.meta` (a mismatch is refused: the file was cut short or changed in a copy); a dump is then read to its end (`pg_restore -f /dev/null`), a snapshot and the uploads archive listed to theirs. A backup with no `.meta`, or one made before sizes and checksums were recorded, is verified by the full read alone. `--force-unverified` restores a backup that failed these checks — whatever is unreadable is lost; for when the file is the only copy.
  - It then checks the credential-encryption key matches (`--ignore-key-mismatch` to skip), asks for the typed `RESTORE` (`--yes` skips it), takes a safety backup of the current database (`--no-safety-backup` to skip; no retention pass, so the backup being restored cannot be pruned) and stops the app containers (keeping `db` up). `tar` runs in the database's own image.
  - **It never ends without saying where things stand.** If `pg_restore` fails, the application is left stopped and the closing summary gives the command that puts the safety backup back. Otherwise the stack is started as a deploy starts it — the backend alone, which migrates the restored schema forward (`alembic upgrade head`), a wait of up to `RESTORE_HEALTH_TIMEOUT` seconds (default 1800), then the workers and the frontend — and the summary reads `RUNNING`, `STILL STARTING`, `NOT RUNNING` or `PARTLY UP` with the next step. A restore that does not end `RUNNING` exits non-zero, as does a cancelled one. `--no-start` leaves the application stopped for the caller to start (`deploy.sh` option 7 uses `--yes --no-start`).
- **`data_repairs.py`** - Show the **data-repair ledger** (table `data_repairs`): the one-off corrections of rows written by older versions, and which of them this instance has run. Read-only. `docker compose exec backend python scripts/data_repairs.py [--pending] [--json]`. `deploy.sh` (after a healthy start) and `status.sh` print the pending ones with the exact command. Nothing runs a repair automatically: the two below stay operator actions, and each records its own run. A run limited to `--project` is not recorded — it does not settle the repair for the instance. A new database (no hosts when the ledger is created) is recorded as needing neither.
- **`merge_duplicate_scanner_findings.py`** - **The way past "N issue(s) have more than one scanner finding"** — the refusal of revision `b2e5a8c1d4f6` when upgrading across v2.448.0. Merges each group of scanner findings that share one issue into ONE finding. Dry run unless `--apply`; `--keep ID` (repeatable) names the finding to keep for its group, otherwise the one furthest along is kept (confirmed, accepted risk, remediated, retest, open, false positive; then the one with report text, the most endpoints, the oldest). The others' endpoints, scanner rows, comments, status history, evidence and proposals move onto it; its EMPTY report-text fields are filled from them and its own text is never overwritten; before anything changes every finding of every group is written whole to `uploads/merged_scanner_findings_<time>.json`. Plain SQL over the database's own foreign-key catalog, so it runs on the schema the refused upgrade left in place and **while the new backend is failing to start** — it holds the migration lock for its whole run, so the backend's retries wait for it (without that the two deadlock): `docker compose exec backend python scripts/merge_duplicate_scanner_findings.py [--project ID] [--keep ID …] [--apply]`, then start the build again (`./scripts/deploy.sh` option 1). A finding listed in an issued client report keeps its number only if it is the one kept — choose with `--keep`.
- **`backfill_misconfigs.py`** - Record misconfiguration-catalog observations from evidence already stored, for imports made before v2.414.0. Idempotent. `docker compose exec backend python scripts/backfill_misconfigs.py [--project ID]`. A run over every project is recorded in the data-repair ledger. Run it when no import is in progress (it writes through the same application-level de-duplication an import uses). It also retitles rows an older import stored under the tool's own title and moves a finding promoted from one onto its catalog check — but **never onto a check that already has a scanner finding in that project** (a project has one scanner finding per issue): that finding is left on its own key, and the pair (`finding #A left as it is; finding #B is the one for check …`) is printed by **every** run until the two are merged by hand — move the endpoints and text you want onto one, delete the other, run it again.
- **`repair_netexec_results.py`** - Correct NetExec rows stored by older parser rules: before v2.428.4, command and module results (`[-] ERROR(…)`, `[+] Executed command…`) stored as logins, and hosts named "None"; before v2.430.1, the NFS mount daemon's ports stored as an "nfs" service (renamed `mountd` only when NetExec alone named them — never 2049, an nmap `-sV` identification or another tool's "nfs"). A dry run unless `--apply`; idempotent. `--project ID` is the numeric project id (`SELECT id, name FROM projects;`); without it every project is checked. `docker compose exec backend python scripts/repair_netexec_results.py [--project ID] [--apply]`. The data-repair ledger records it when it is settled for the whole instance: an `--apply` over every project, or a dry run over every project that found nothing to correct (ports it reports as left alone because another tool named them, `nfs_ports_kept_other_tool`, are not something to correct).
- **`test-alembic-roundtrip.sh`** - Pre-release sanity check (run it locally — there is no hosted CI; `check.sh` runs it as its last step): spins up a throwaway Postgres — the image `docker-compose.yml` names, or the running `db` container's when that tag is not on the host — and verifies every migration's `downgrade()` reverses cleanly (upgrade → downgrade → upgrade), then `alembic check`.
- **`apply_scope_labels.py`** - Bulk-assign subnet labels to a project's scope from a CSV (CIDR column + label column). Runs inside the backend container, matches CIDRs to existing subnets, find-or-creates each label, and assigns it. Idempotent and **dry-run by default** (pass `--apply` to write):
  ```bash
  docker compose exec backend python /app/scripts/apply_scope_labels.py \
      --project-id <ID> --csv /app/scripts/labels.csv          # dry run
  docker compose exec backend python /app/scripts/apply_scope_labels.py \
      --project-id <ID> --csv /app/scripts/labels.csv --apply  # write
  ```
  Columns default to CIDR=0, label=1, comma-delimited (override with `--cidr-col` / `--label-col` / `--delimiter`); `--color <palette>` colors any labels it creates. The dry run lists unmatched CIDRs so you can validate before applying.

## User Management

A default admin account is **created automatically** on first application boot when no admin user exists in the database.

### Default Admin Credentials

On first startup, when `DEFAULT_ADMIN_PASSWORD` is unset, the backend generates a secure random password and **writes it to a file** (it is **not** logged):

```
./uploads/initial-admin-password.txt   (mode 0600)
```

Read it there, log in as `admin`, and change it immediately. Startup **fails closed** if that volume isn't writable — set `DEFAULT_ADMIN_PASSWORD` (or fix the `uploads` volume) rather than ending up with an unrecoverable admin. The file is removed once the password is changed.

> **2FA:** `REQUIRE_2FA` defaults to `true`, so the first login walks the admin through TOTP enrolment. Set `REQUIRE_2FA=false` in `.env` to make it opt-in.

### Controlling Default Admin via Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `DEFAULT_ADMIN_USERNAME` | `admin` | Initial admin username |
| `DEFAULT_ADMIN_PASSWORD` | *(random → `uploads/initial-admin-password.txt`)* | Initial admin password |

### Creating Additional Users

Use the admin web UI at **Administration → System** (`/system-settings`) or the API:

```bash
# Via API (requires admin JWT token; nginx proxies /api on :443)
curl -k -X POST https://localhost/api/v1/auth/register \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"username": "analyst1", "email": "analyst@example.com", "password": "SecurePass123!"}'
```

## User Roles

There are two layers. The **global** role is binary — **admin** (user management, system settings, the audit log) or **member** — and gates nothing else. Everything else is a **per-project** role (a user can be analyst on one project, viewer on another):

- **ADMIN**: Manage project membership, plus everything an analyst can do
- **ANALYST**: Scope management, scan upload, triage, host tests, notes; an agent session started by an analyst can write
- **AUDITOR**: Read-only access with audit-log visibility, exports and reports; can start a read-only agent session
- **VIEWER**: Read-only access to scan results and dashboards

## Password Requirements

Passwords must meet these criteria:
- At least 12 characters long
- Contains uppercase letters
- Contains lowercase letters
- Contains numbers
- Contains special characters (!@#$%^&*()_+-=[]{}|;:,.<>?)

## Script Dependencies

- **Inside the backend container** (the seeds, `apply_scope_labels.py`, `backfill_misconfigs.py`, `repair_netexec_results.py`): the running stack — `scripts/` is bind-mounted at `/app/scripts`.
- **Stack management** (`deploy.sh`, `status.sh`, `backup-db.sh`, `restore-db.sh`, `upgrade-instance.sh`, `test-alembic-roundtrip.sh`, `check.sh` — which also needs Node for the frontend step): Docker and Docker Compose on the host. `collect-logs.sh` also needs `python3`.
- **Host-side helpers** (`rdap-lookup.py`, the certificate generators): neither the stack nor a database.
