# BlueStick Architecture

> **Last verified against:** backend 2.427.1 / frontend 5.309.1 (2026-09-26); the areas changed since then were re-checked against 2.450.0 / 5.329.0 (2026-10-02)

BlueStick is a multi-user, multi-project pentest-operations platform that ingests scanner output, deduplicates hosts, correlates them to project scopes, enriches findings with vulnerability data, and records agent-assisted testing: tests proposed on hosts and the evidence of what they produced. This document is the canonical architecture reference — update it when domains, endpoints, or workflows change materially.

- **Frontend container** (`networkmapper-frontend-1`) runs Nginx to terminate TLS, serve the Vite build, and reverse-proxy `/api/*` to the backend. The SPA is built on Tailwind v4 + Radix (shadcn-style primitives) + Sonner + lucide-react — Material UI was fully removed in the v4 frontend line (the app is now on the v5 line). Charts with real axes use **Observable Plot** (`components/charts/PlotFigure.tsx`, 5.307.0); the address terrain (on the Posture overview since 5.330.0) is **three.js** (`components/operations/TerrainScene.tsx`), loaded as a lazy chunk only when scrolled near; small inline visuals stay hand-built SVG.
- **Backend container** (`networkmapper-backend-1`) runs `uvicorn app.main:app` with multiple workers. Exposes `/api/v1` and `/health`.
- **Worker container** (`networkmapper-worker-1`) runs `python -m app.worker` — a single long-lived process that LISTENs on the Postgres channel `ingestion_jobs`, polls for queued work with `SELECT … FOR UPDATE SKIP LOCKED`, processes each job through the parser pipeline, and reaps orphaned jobs whose heartbeat has gone stale. The backend writes upload files to a shared volume; the worker reads from the same path.
- **Report-worker container** (`networkmapper-report-worker-1`) runs `python -m app.report_worker` (v2.196.0) — a sibling of the ingestion worker that LISTENs on the `report_jobs` channel and does the report jobs off the request path — an issue's render is claimed before a preview, a repeated preview by the same requester supersedes the earlier one, and a render touches the worker heartbeat between formats: the host inventory's JSON download and the Quarto client-report renders (the inventory CSV streams synchronously from the API; the HTML host report, the agent package and the Markdown bundle were retired with "Export hosts", owner 2026-10-07). Both workers share the same LISTEN/poll/reconnect/heartbeat/reaper machinery in **`app/worker_loop.py`** (`run_listen_loop`, `install_signal_handlers`, `write_heartbeat`); each entry point only supplies its channel name and per-job processing callback. The report-worker has its own heartbeat-freshness healthcheck (own heartbeat path, reuses `WORKER_HEARTBEAT_TIMEOUT`) and a `mem_limit`. The JSON streams every matching host chunk by chunk (`REPORT_STREAM_CHUNK`) straight to the artifact file (`ReportGenerator.write_json_report`, v2.394.0; 80k hosts: ~80 s, ~0.5 GB peak, a 2.6 GB file), so nothing is capped — there is no host-cap setting. The async report pipeline is covered in §8.
- **Database container** (`networkmapper-db-1`) runs PostgreSQL 16 with a persistent volume for data. Schema is owned by **Alembic** — `alembic upgrade head` runs on every backend boot before the app serves traffic. The previous startup-DDL compatibility path (`Base.metadata.create_all` plus a hand-rolled migration list in `app/db/init.py`, and `_ensure_schema` calls in services) has been retired; `app/db/init.py` now does nothing but bring the database up to the Alembic head (serialized across the API + worker processes). **How the boot migration behaves (review 2026-10-01 B1):** every process migrates at start, one at a time, under a session-level advisory lock. A process that does not get the lock POLLS `pg_try_advisory_lock` on an autocommit connection that is idle between tries (it logs `waiting for another process to finish database migrations` every 15 s and gives up after `DB_MIGRATION_LOCK_TIMEOUT`, default 3600 s) — it used to block inside `pg_advisory_lock`, holding a snapshot that a `CREATE INDEX CONCURRENTLY` in the migrating process waited on, and boot hung for ever. `alembic/env.py` runs the whole upgrade in one transaction and the current revisions build their indexes inside it (`c3f6b9d2e5a7`; only older revisions in the chain still use an autocommit block), so a failed upgrade normally leaves the database at the revision it started from. The failure line reads the database to say which case it is: `DATABASE MIGRATION FAILED — NOTHING WAS CHANGED` (still at the starting revision, which the previous build runs: roll the build back, no restore) or `… schema left PARTWAY at revision …` (restore the pre-deploy backup). Boot also warns about INVALID indexes an interrupted concurrent build left (`REINDEX INDEX CONCURRENTLY <name>`). The model is the schema, and Alembic enforces it. Migrations live in `backend/alembic/versions/` (~150 revisions at v2.450), baseline at `b46cd59c17f5_baseline_schema`, one linear chain — a second head is a merge bug. No head is named here on purpose: it moves every few releases. Trust `alembic heads` / the `versions/` dir over any chain quoted in prose.

A single `docker-compose.yml` wires all five. `scripts/deploy.sh` is the unified entry point (first-time setup, rebuild, reconfigure IP, nuclear cleanup, security status, `.env`/SSL backup, roll back — §11).

## 2. Identity, multi-tenancy, and access control

BlueStick has **two parallel authentication systems** because it serves two very different consumer types.

### 2.1 JWT (human users)

- Users live in `users` (`app/db/models_auth.py`). **The global role is binary** — `ADMIN` (user management, system settings, audit log) or `MEMBER` (v2.46.0). The four-tier vocabulary — admin > analyst > auditor > viewer — is the **per-project** `ProjectRole` on `ProjectMembership.role` (`models_project.py`), which is where every granular check happens.
- `POST /api/v1/auth/login` returns a JWT signed with `settings.SECRET_KEY`. Sessions are tracked in `user_sessions` so tokens can be revoked server-side.
- A default admin account is seeded on first boot by `app/startup.py` with `must_change_password=True`. Its password is `DEFAULT_ADMIN_PASSWORD` when that is set to something other than the literal `admin`, otherwise a random one written mode 0600 to `uploads/initial-admin-password.txt` and never logged — there is no `admin`/`admin` account; the forced-change flow gates every JWT-bearing request behind `require_password_changed` until the user rotates the password.
- RBAC checks are enforced in endpoint dependencies: `require_role(...)` gates ADMIN only; everything granular is the project-scoped `require_project_role(...)`.
- **Two-factor (TOTP)** — **enforced by default** (`REQUIRE_2FA=true`): a login without an enrolled second factor is walked through `ForceTwoFactorSetup` before any data endpoint answers, the same way `ForceChangePassword` gates a fresh password. Recovery codes live in `user_recovery_codes`; an admin can reset a user's 2FA. Users enrol an authenticator app via `/api/v1/auth/2fa/*` (`two_factor.py`): `setup` returns the provisioning secret/QR, `enable` verifies a code and returns one-time recovery codes, `disable` / `recovery-codes` manage the rest. TOTP secret + recovery state live on the `users` row; login challenges the second factor when 2FA is enabled.

### 2.2 Agent sessions and keys (non-human agents)

- Terminal-side agents (Claude Code, Codex, manual curl) authenticate with an `X-API-Key: nm_agent_...` header. Keys are `APIKey` rows in `api_keys` (`models_auth.py`), hashed at rest; the plaintext is shown to the operator exactly once.
- **A key binds to ONE project-scoped `AgentSession`** (`agent_sessions`, `models_agent.py`). A key is not limited to one kind of work and carries no capability grants. **The key's authority is its OPERATOR's project role**, re-resolved on every request by `enforce_agent_operator_access` (`app/api/deps.py`), mounted on every `/agent/*` router: writes need the operator to hold `analyst`, bulk exports `auditor`; a role change, a removed membership or a deactivated account reaches keys already in the field immediately. Session-metadata writes (renew, end, feedback, tool suggestions) are exempt from the write floor. What a route needs beyond the defaults (a read needs membership, a write `analyst`) is declared ON THE ROUTE — `dependencies=[Depends(agent_read_floor(ProjectRole.AUDITOR))]` or `Depends(agent_session_metadata_write)`, on the route or in its `APIRouter(...)` constructor — and the gate reads it off the matched route (`deps.agent_route_access`); a dependency passed to `include_router(...)` is not part of the route object and is not seen. The gate stamps `request.state.key_operator_id` and `request.state.agent_project_id` for the handlers, and an agent call's authentication is one joined select (key, session, operator, membership) plus the rate-limit upsert.
- **A password change takes the account back from its agents.** A key issued before its operator's `password_changed_at` is refused with 401 `{"error": "operator_credentials_changed", "recoverable": false}`; an admin's reset-password, the user's own change-password and an admin's reset-2fa also end the user's agent sessions (`agent_session_service.end_sessions_of_operator`). A session resumed afterwards carries a key minted after the change, and works. Self-service 2FA disable does not end sessions (it needs a live session and the password; it is not a recovery action).
- **The operator drives; the agent opens its own work.** An agent reads a scope by id (`/agent/scopes/{scope_id}/subnets|domains` and the target files `hosts.ndjson` / `live-hosts.txt` / `web-targets.txt` / `named-targets.ndjson`). Uploads belong to the session (`POST /agent/uploads` → an `IngestionJob` with `agent_session_id`; batches keyed `(agent_session_id, label)`). `POST /agent/host-tests` puts individual tests on hosts (`host_tests`, shown on each host's page) and `POST /agent/evidence` records what the agent ran, naming the test it answers — nothing to open first and no approval step (§5). Each row carries the `agent_session_id` of the session that wrote it; a session may write any number, in any order. `agent_session_service.end_agent_session` — the one path for the operator's End, the agent's `end_session` and the hourly lapse sweep — revokes the keys; nothing else needs closing, because tests and evidence are project data that another session or a person carries on. The safety rules (`agent_policy.SAFETY_RULES`) are the agent's contract, which the server cannot enforce: show every command, the operator drives, stay in the declared scope, write into the working directory, record every command.
- Sessions are started by an operator from **Operations → Start Agent Session** (`POST /projects/{id}/assist/start` — the one entry point since v2.433.0; pages about one object open the same dialog with a one-line task), listed and ended at `/projects/{id}/agent-sessions`, and resumed with key rotation (`…/agent-sessions/{sid}/resume`). Keys default to 24 h (`AGENT_KEY_TTL_HOURS`) and the agent can renew its own while the session is under `AGENT_SESSION_MAX_LIFETIME_HOURS` (168 h). **Ending the session, not expiry, is the revocation control.**
- The `/api/v1/agent/*` surface is its own set of FastAPI routers — physically separate from the JWT-user surface — and is **exempt** from `require_password_changed` because the agent has no credentials to rotate. `POST /api/v1/mcp` serves the same endpoints as MCP tools by looping back in-process with the caller's key; **the MCP layer makes no authorization decision**.

### 2.3 Project scoping

Every data-bearing endpoint (upload, hosts, scans, scopes, host tests, etc.) is nested under `/api/v1/projects/{project_id}/...`. The `get_current_project` dependency loads the project, verifies the JWT user is a member, and enforces the required role. Cross-project reads/writes are blocked at the dependency layer; a second project's data is invisible unless the user is explicitly a member.

Portfolio-level endpoints (`/api/v1/portfolio/dashboard`) are global — they return cross-project summaries of the projects the caller belongs to (a global admin sees every non-archived one). Oversight (`/api/v1/oversight/dashboard`, v2.377.0) is the administrators' programme view of EVERY registered project, archived included; its router is mounted with `require_role(ADMIN)`, so members and project admins get 403. Both read the same counting services (§3, "Cross-project counts").

## 4. Scan ingestion pipeline

Uploads flow through an asynchronous worker so the request path never blocks on parsing. The flow is deliberately unforgiving of crashes — every state transition is durable in Postgres.

0. **Staged review (the UI path, v2.351.0+).** The Scans page uploads with `stage=true`: the job is registered as `staged`, no worker touches it, and `staged_import_service.detect_for_job` reports each candidate format with its *basis* — recognised by `structure`, by `filename` only, or a `fallback` the dispatcher would merely try. The operator reviews (`UploadReviewDialog` + `useUploadReview`), optionally chooses a format, and `POST /upload/jobs/{id}/start` moves the job to `queued` under a row lock. An identical file already in the project (a scan, or a staged/queued/processing job — SHA-256) is refused with 409 `duplicate_scan`, and start re-runs that check. Files are retained `INGESTION_RETAIN_FILES_DAYS` (default 7) after a job finishes so a wrong format can be retried or the file re-processed; an unstarted staged job expires after 24 h. Agents and direct API callers skip staging and queue immediately. **The real parsers can never be dry-run** (they write and commit incrementally), so a preview is detection plus a read-only sample, never a parser run.
1. **Upload arrives.** `POST /api/v1/projects/{id}/upload/` streams the file to `uploads/ingestion_queue/{job_uuid}/{safe_filename}`. `ingestion_service.create_job`:
   - slugifies the filename to prevent log injection and FS traversal,
   - enforces `MAX_FILE_SIZE` chunk-by-chunk during the stream,
   - runs `_validate_content_matches_extension()` — a magic-byte check that rejects the obvious nonsense (`.xml` that doesn't start with `<`, `.json` that doesn't start with `{` or `[`, text files with NUL bytes),
   - writes an `ingestion_jobs` row with status `queued`,
   - fires `pg_notify('ingestion_jobs', job_id)` to wake the worker.
2. **Worker claims the job.** `poll_and_run_one()` claims the oldest queued job through `job_transitions.claim_oldest_queued` (`FOR UPDATE SKIP LOCKED`), transitions it to `processing` inside the same transaction (so competing workers skip it) and records `claimed_at` as a fencing token that conditions the later heartbeat / complete / fail writes, then runs outside the row lock. Before the claim commits, the attempt takes a session-level advisory lock keyed by (job, claim) on a connection of its own (`hold_attempt_liveness`) and holds it until it finishes: a worker that dies releases it with its connection, which is how a dead attempt is recognised at once (step 6). Every job status write goes through `job_transitions`.
3. **Parser dispatch.** `_process_job` sniffs the file sample, builds a list of parser attempts (most-specific first), and executes them in sequence. The first parser that returns a non-empty result wins. Each parser call is wrapped in a `ParseFailure` boundary so a crash records a `parse_errors` row with a user-facing message and binds the ID back onto the job.
4. **Heartbeat.** Every parser calls `report_progress(...)` between records (`parser_utils.ProgressBeat` for the record-loop parsers), which reaches `service.update_heartbeat`. The heartbeat renews the lease with one fenced UPDATE (no read of the job row), commits the work so far, and is the cooperative stop point: a job cancelled by a user or past `INGESTION_JOB_TIMEOUT` raises `ParseFailure`, and a worker that is shutting down raises `ShutdownRequested`, which hands the job back to the queue instead of failing it. A heartbeat whose lease write matches no row (the job was cancelled from the API process, or reaped and re-claimed) rolls the pending batch back BEFORE raising — an attempt that no longer owns the job commits nothing.
5. **Terminal state.** Success → `status='completed'`, `scan_id` set, `tool_name` set. Parse failure → `status='failed'`, `retry_count++`, `last_error` populated with a trimmed traceback or the user message. Unexpected exception → same, but with a `traceback` last_error. (`retry_count` counts failures and operator retries; the reaper has its own counter, `reap_count` — step 6.) An operator's *Start* and *Retry* are one path (`staged_import_service.queue_job`): both re-run the duplicate guard, so retrying a failed job whose identical file was imported since answers 409 `duplicate_scan` unless the job carries `options.allow_duplicate`.
   **An import that does not finish leaves no scan and nothing that only it created.** Because parsers commit as they go, the scan a parser creates is stamped on the job row (`ingestion_jobs.in_progress_scan_id`, `note_scan_created`) in the transaction that first commits it, and cleared on completion; that column is the only record of an attempt's scan. On a failure, cancel, timeout or shutdown the dispatcher calls `delete_partial_scan` (once, in `_process_job`, before any fallback parser is tried): the scan, the hosts and ports only that attempt created (their history rows say `host_created` / `port_created` for this scan and no other scan saw them — never a host with work on it, the one list `host_work.work_kinds`: a note, review, tag, finding endpoint, test, evidence record, remediation entry, a proposal about one of its observations or an operator's name for it; nor one that anything from another scan hangs on), the observations, scripts, host scripts and host attributes no other scan reported, its name observations and the names only it observed that nothing else refers to (`dns_name_service.delete_scan_observations`), and — after the delete commits — the EyeWitness screenshots it extracted (`uploads/web_screenshots/<scan id>/`). Every port insert stamps the row with the scan that created it (`ports_v2.created_scan_id` — the dedup service, masscan's INSERT and the Nessus path's `_get_or_create_port`; read only by the two scan deletes and the hand delete's preview, never by a page or a count), and the cleanup deletes the ports carrying this scan's stamp under the same guards (`ingestion_service.delete_ports_scan_created`, the one port step, which a scan delete by hand runs too — below); for Nessus, which writes no port history, the stamp is the only record. A worker killed outright cannot clean up; the id on the job row lets the next claim of that job (or the reaper, when it fails the job for good) do it before anything else is parsed.
   *Not undone:* updates the attempt made to hosts and ports that already existed, and confidence conflict history (`documentation/PARSERS.md`, "What a failed import leaves"). A name the attempt introduced stays only when something else holds it: another observation (another scan's, an import's, a test's), the person who added it, a host test, finding endpoint, scanner observation or another scan's web interface naming it, or a scope domain covering it.
   *A scan deleted by hand* (`DELETE /scans/{id}`, project admin) removes everything the scan brought that nothing else holds — the scan was imported into the wrong project, or should not have been imported, and must leave nothing behind. It shares the cleanup's three steps — `scan_sightings.release_scan` (which deletes the scanner observations, scripts and attributes only that scan reported; never an observation a finding or a proposal refers to), `ingestion_service.delete_ports_scan_created` (the ports it created on hosts that stay, found by the stamp and by port history, under the `_port_is_only_this_attempts` guards — which keep a port that carries a scanner observation a finding or a proposal refers to, so a kept observation keeps its port on both delete paths) and `dns_name_service.delete_scan_observations` — and the cleanup's provenance guards for hosts (`host_provenance_conditions`: a host another scan or source attached anything to is kept). It differs in one thing on purpose: a host only that scan brought goes whether it was worked on or not. It is refused (409 `import_running`, nothing changed) while a live attempt is processing an import of the project (`ingestion_service.running_import`: a `processing` job whose attempt lock is free or whose lease is dead does not count), and otherwise holds the project's cleanup lock to the end of its transaction, whatever the scan. What it cannot undo: values the scan overwrote on hosts, ports, scripts and observations that already existed — no previous value is kept. The preview (`GET /scans/{id}/deletion-impact`) counts and lists the removed hosts that carry work (`host_work.work_on_hosts`, the cleanup's own list, one grouped statement) and the delete answers 409 `hosts_with_work`, changing nothing, until the request says `confirm_hosts_with_work=true`; the check runs in the delete's transaction on the set it deletes, with those host rows locked. Every figure of the preview is counted with the condition the delete applies (`hosts_scan_brought`, `ports_scan_created_condition`, `scan_sightings.removed_with_scan` / `kept_without_scan`); the hosts are chosen before `release_scan` runs, so the guards also read the sightings of other scans directly (`before_release=True`) and give the same answer before and after it.
   *A cleanup that runs late* — the dead job is reaped or re-claimed after another import of the same hosts completed — keeps what that import re-observed: a row's `scan_id` is "first recorded by" and never moves on a re-observation, every scan that reports a script, host script, host attribute or vulnerability writes a sighting row, and `scan_sightings.release_scan` — run before any scan row is deleted, by the cleanup and by `DELETE /scans/{id}` — deletes what only that scan reported and hands the rest to the earliest other scan that reported it (a vulnerability's `last_seen_scan_id` to the latest); confidence rows go to a later scan with history; and the cleanup treats a later scan's `last_updated_scan_id` / `last_seen_scan_id` as protecting the port and host.
   *Concurrency (more than one worker):* every transaction of an import takes a per-project PostgreSQL advisory lock in SHARED mode when it begins (`project_import_lock`, installed by `_run_job`; imports never wait on each other, and it is released at each batch commit); `delete_partial_scan` takes it EXCLUSIVE, so its "no other scan saw this" checks run with no import batch of that project open and cannot miss a re-observation in flight. A cancel issued from the API waits at most 15 s for it.
   *A cleanup that fails* leaves the scan named on the job row, and the job is never parsed over it: a claim that cannot remove the previous attempt's scan fails the job (`job_transitions.fail`), and a parser failure whose committed scan cannot be removed ends the fallback chain. The reaper pass (step 6) also retries the cleanup of `failed` jobs that still name a scan once their attempt is over (its liveness lock is free, or its lease is past the stale window) — which is how a `processing` job cancelled while its worker was dead is cleaned (a cancel whose attempt is already over cleans up at once). Cancel is decided from the job row alone; there is no in-process cancel list.
6. **Orphan reaping.** On a monotonic deadline of ~12 poll intervals (~1 min, idle or busy — `worker_loop.run_listen_loop`'s `periodic` callbacks, beside the backlog check, the webhook sweep and the remediation sweep — deadline alerts, then the day's count per project — which limits itself to one run per 15 minutes), the worker runs `reap_orphaned_jobs()` (and once at boot): a `processing` job whose attempt no longer holds its liveness lock (`attempt_is_over` — the worker is gone), or, as the fallback, whose heartbeat is older than `INGESTION_JOB_TIMEOUT` × `INGESTION_ORPHAN_CUTOFF_MULTIPLIER` (default 1.5), is re-queued automatically while `reap_count` ≤ `INGESTION_MAX_RETRIES` (default 2) and its upload is still on disk; otherwise it fails with a "worker likely crashed" message and admins are notified. `reap_count` counts the reaper's re-queues only and is reset when an operator queues or retries the job. Closes the gap when a worker dies mid-parse.

**Retained files.** A finished job's upload stays `INGESTION_RETAIN_FILES_DAYS`; the sweep (and a discard or expiry) removes the file under the row lock that decides it and stamps `ingestion_jobs.file_removed_at` in the same transaction. The sweep skips stamped rows and `file_retained()` reads the column; start / retry / reprocess still check the disk.

Inside a parser, two rules keep one bad record or byte from failing the import: a parser that skips a failing record wraps it in `parser_utils.record_savepoint` (a failed flush otherwise poisons the whole session), and a parser whose text lines reach a Text column reads the file with `parser_utils.read_tool_text` (UTF-16 decoded, NUL removed — PostgreSQL rejects NUL). A parser may also report the lines it did not interpret as redacted shapes (`ingestion_jobs.uninterpreted_lines`, §3). Files uploaded together form a `ScanBatch`; a failed or partial import stays on the attention list until dismissed or superseded by a clean import of the same file (`import_attention_service`).

Parsed hosts flow through `host_deduplication_service` (dedupe by IP within project), `subnet_correlation` (bind hosts to scopes via an IP trie), and `vulnerability_service` (enrichment). `ports_of_interest` is the catalog of exposed services that the subnet insights and Operations read.

## 5. Host tests + agent workflow

Agent-assisted testing is recorded as **host tests** and **evidence records**: what was proposed for a host, and what was actually run against it. The `/api/v1/agent/*` surface is split into routers by KIND OF WORK — `agent_browse` (shared reads, identity, session lifecycle), `host_tests` (its agent router), `agent_proposals` (evidence + proposals), `agent_recon` (scope reads + uploads), `agent_assist` (plus `agent_browse.renewal_router` and the agent feedback router; `agent_activity` is the JWT viewer of the call log, not part of this surface) — but since v2.337.0 that split is code organisation, not authorization: **one project-scoped session and key reaches all of them** (§2.2). There is no required order and no approval step (v2.433.0): the operator drives, and the agent works within the operator's project role.

### 5.1 Host tests

A `HostTest` (`models_host_tests.py`) is one check on one host: `tool`, `description`, `command` (with `{ip}` / `{fqdn}` placeholders), `rationale`, `expected_result`, `references`, `priority`, a free `label` (a batch of proposed tests shares one), optional `target_fqdn` / `name_id` (a name observed at the host — the snapshot survives the name's deletion), `status` (`proposed` → `in_progress` → `done`, or `dismissed` with a reason, who and when), `assigned_to_id`, `tester_summary`, `source` (`agent` | `person`) and the proposer's attribution (user, session, model, client, prompt version). It belongs to its host (`ON DELETE CASCADE`) and is shown on the host page's Tests section; there is no project-wide tests page.

- **One contract for people and agents.** `endpoints/host_tests.py` builds its router once (`make_router(reader, writer)`) and `api.py` mounts it twice: under `/projects/{id}` for the JWT user (any member reads, `analyst` writes) and under `/agent` for the session key (the router-level operator gate decides writes). Both call `host_test_service` with the same Pydantic schemas (`schemas/host_test_schemas.py`), and the MCP tools `host_tests_propose|list|get|update` advertise those schemas.
- **Creation is a validated batch** (1–200) and is idempotent per test: `request_key` (unique per project) plus a hash of the content — the same key and content returns the existing row, the same key with different content is a `409`. An unknown host fails the whole batch.
- **Updates are revision-checked.** `PATCH` carries `expected_revision`; the update is one conditional `UPDATE … WHERE revision = :expected`, so a stale write changes nothing and answers `409`. `done` needs an evidence record or a `tester_summary` saying why none was run; `dismissed` needs a reason.
- **No approval gate.** A proposed test is visible at once. Which hosts and which tests is the operator's request to the agent; the server has no selection policy.
- **Planned / tested** are two SQL definitions in `host_test_queries.py`, used by the Hosts list and DSL (`has:planned`, `has:tested`), `/coverage`, the per-host assessment (`host_assessment_service`), Evidence and the address terrain (on Posture): *planned* = the host has a test that is `proposed` or `in_progress`; *tested* = the host has an evidence record whose outcome is `finding`, `no_finding` or `inconclusive`. *Untouched* (`host_query_predicates.untouched_conditions`) = no follow, note, non-dismissed test, evidence record or finding endpoint.
- **My Tasks** (`operations_read_service.compute_my_tasks`) is the tests still to do that are assigned to the caller, on a host they have in review, or unassigned and critical/high; `project_signals_service.open_tasks` and the engagement tester rows count active host tests the same way.

### 5.2 Working a test: evidence

The agent is a **coordinator, not an executor**: the operator's terminal runs every command, under the client's sandbox. To work a test the agent (or a person) moves it to `in_progress`, runs the command, and records what came back with **`POST /agent/evidence`** — `host_test_id`, a `request_key` (required with a test; a retry returns the stored record), the command as run, the outcome, a summary and the raw output — then marks the test `done`. Evidence is immutable (§5.7). When the test was aimed at a name (`target_fqdn`) and the record carries `observed_ip` with a test outcome, `agent_evidence_service` writes the name's `TESTED` observation through `dns_name_service.record_observation(evidence_record_id=…)`; a failed attempt, an `info` record or a record with no observed address binds nothing.

**Remediation tracking (v2.457.0)** follows the same shape. `endpoints/remediation.py` builds one router (`make_router(reader, admin)`) mounted under `/projects/{id}` (auditor reads, project admin writes) and under `/agent` (the reads' floor is declared on the agent router with `agent_read_floor(READ_ROLE)` — one constant, `remediation.READ_ROLE`, for both mounts; `agent_admin` requires the key's operator to be a project admin). `remediation_service` holds two tables (`models_remediation.py`): `finding_host_remediation`, one-to-one with `finding_hosts` (contact, date notified, status open / closed / deferred, closed date; a row exists once something was recorded), and `remediation_events`, the HOST's timeline of field changes and notes, whose links to the finding go null when it is deleted while the title stays. `apply` is the one write path for the page's bulk edit and an agent's file-driven fill: targets resolved and validated before anything is written, a conflict left alone without `overwrite`, a dry run that reports the same plan. Every read takes a SET of project ids and the rows carry `project_id` with an index on `(contact_email, status)`, so a cross-project lookup by contact is the same statement. The page (`/remediation`, `pages/Remediation.tsx`, 5.335.0) is one paged table over `GET /remediation` with its filters in the URL; `RemediationEditDialog` edits one row or a selection through `apply` (it sends only the fields that were changed, with `overwrite`), and `RemediationTimeline` is the host's timeline in a side sheet. It is deliberately not connected to `findings.status`, `finding_hosts.host_status`, Posture, Operations or the client report: a project is still one assessment window, and this is a side record of the client's progress. **The two statuses record two facts and each has one name:** the record's `closed` is the contact's claim, shown as "Reported fixed" (never "Closed"); the endpoint's `remediated` is the assessor's conclusion, "Remediated". Stored values and API enums are unchanged — labels and documentation only. Nothing writes one from the other, so the gap is derived: `remediation_policy.verification_expr` (one SQL `CASE`, beside `state_expr`) gives a listed row `reported_fixed_not_retested` (record closed, endpoint neither remediated nor a false positive), `remediated_record_open` (endpoint remediated and a record that exists is open or deferred — since v2.468.0 an endpoint nobody tracked is not one) or NULL. The list returns it per row as `verification`, counts both as `verification_counts` in the statement that already counts the states (before the state filters, so each count is the list `verification=` opens), and filters by it on all three mounts; the page shows the counts as buttons and the gap as a line in the row's Deadline cell. The list's membership is not widened for it. Every writer of the records (`apply`, a recorded follow-up, an endpoint's removal) locks through `_lock_for_write` — the `finding_hosts` rows in id order, then their records.

**When a finding leaves a host.** A remediation record is deleted with its `finding_hosts` row (the foreign key cascades), and a restored endpoint is a new row. So every path that removes an endpoint or a host from a finding, or deletes a finding, first calls `remediation_service.before_endpoints_removed` in the same transaction. With tracking on, a record that holds anything — a contact email or name, a team, an assigned date, a status other than open, a follow-up — is the project admins' to give up: anyone else gets a 409 and nothing is removed; for a project or global admin each such record is written to its host's timeline as a `change` entry with `field: "finding"` saying what it held (the timeline outlives the record; the page prints it as "Finding removed from this host" / "Finding deleted"). With tracking off the call does nothing and no response mentions remediation.

**Per installation, with deadlines (v2.461.0 / 5.340.0).** Whether remediation is tracked at all is the installation's decision, not a project's: `remediation_policy` is a single-row table (`RemediationPolicy`, id 1 — `enabled`, off by default; days per severity, 30 / 30 / 90 / 120 and none for informational; `due_soon_days`, 7; `time_zone`, an IANA name, UTC by default), read by any signed-in user through `GET /remediation-policy` and written by a global admin through `PUT /remediation-policy` (audited as `remediation_policy_updated`; System settings → "Remediation tracking", `RemediationSettingsSection`, directly under worker health since 5.341.0). The per-project switch `projects.remediation_in_oversight` (v2.458.0) was dropped by revision `b5e2c9d7f4a6`. **Off means nothing about remediation anywhere**: `make_router` carries the `enabled` dependency, so every remediation route — JWT and agent — answers 404 "Remediation tracking is not enabled on this installation."; `engagement_metrics_service.remediation_counts` returns nothing, so Oversight's `remediation` blocks are `null`; the alert sweep is a no-op; and the frontend (`hooks/useRemediationPolicy`, the `feature: 'remediation'` flag in `config/navigation.tsx`) lists no Remediation entry. Some installations use BlueStick only to collaborate on reports, and for them "no target, nothing is ever called overdue" still holds. Recorded data is kept while the feature is off.

`remediation_policy.py` is the ONE definition of a deadline: the assigned date (`notified_on`, labelled "Assigned on" in the UI) plus the installation's days for the finding's CURRENT severity. It is derived while a row is open (`due_expr`, SQL only — there is no Python copy) and never stored, so a changed timeline or severity moves every open deadline at once; closing a row freezes the deadline then in force in `finding_host_remediation.closed_due_on` (`_freeze_closed_deadlines`, one UPDATE that evaluates `due_expr`; correcting the assigned date of a row that is already closed re-freezes it against the severity and timeline of the day of the correction, since the earlier ones are kept nowhere). "Today" is `Policy.today()` everywhere — the installation's calendar day in `remediation_policy.time_zone` (assigned and closed dates are entered by hand from a local calendar; compared with the server's UTC day, rows went overdue mid-afternoon west of Greenwich). There is no day of allowance either way: a date after the installation's day is refused. `state_expr` gives each row one state, in this order: `closed`, `deferred` (the clock is stopped), `no_deadline` (the severity has no timeline), `not_assigned` (no assigned date — the clock never started, so it cannot read as overdue), `overdue`, `due_soon`, `on_track`. The list, its `state_counts` (and `status_counts`, summed from them), the contacts' counts, the cross-project table and Oversight all evaluate that one expression.

**Follow-up by contact.** `remediation_service.contacts` returns each contact's rows by state, the most overdue first; `follow_up` returns one contact's overdue and due-soon rows and a plain-text message — the server sends nothing; `record_follow_up` writes one immutable `follow_up` timeline entry per row and the day on the row (`last_follow_up_on`), leaving alone a row already followed up that day. The preview lists at most 500 rows (`FOLLOW_UP_MAX_ROWS`) and carries `total` (every at-risk row of the contact) and `not_listed` (how many the list and the message leave out, which the message says); recording covers every at-risk row, listed or not. A `followed_up_on` after the installation's day is a 422. Routes: `GET` / `POST /remediation/follow-up` on both mounts (MCP `remediation_follow_up`, `remediation_record_follow_up`); UI `RemediationFollowUpDialog`.

**Across projects.** `remediation.account_router` is mounted at the API root, not under `/projects/{id}`: `GET /remediation-overview` (rows), `/remediation-overview/projects` (per-project state counts and totals), `/remediation-overview/contacts` and `/remediation-overview/follow-up` read the same service functions over the SET of projects the caller administers — every project for a global admin — archived projects included. The whole per-project contract is mounted a third time at `/remediation-overview/projects/{project_id}/remediation…` (`administered_project`), because the ordinary project routes answer 410 for an archived project while remediation continues until every finding is dispositioned. `/remediation-overview/teams` and `/remediation-overview/trend` (v2.462.0) are the same two reads over that set. The page is `/remediation-deadlines` (`pages/RemediationDeadlines.tsx`, in the sidebar beside Portfolio and Oversight): a table of the projects by state, then `RemediationWorkList`, the work list it shares with the project's Remediation page. On it a row's host and finding open in that row's project when the reader can switch to it (`selectProject`, then the page) and are plain text otherwise — an archived project, for instance. There is no agent route for the cross-project reads — an agent key is bound to one project.

**What a manager asks first (v2.462.0 / 5.341.0).** `list_rows` returns, with the rows and over the same selection, `severity_counts` (overdue and due soon per severity, counted BEFORE the severity filter so choosing one severity does not empty the table), `overdue_ages` (the overdue rows in `remediation_policy.OVERDUE_BANDS` — 1–7, 8–30, 31–90 and over 90 days past the deadline, by `overdue_band_expr`, which is NULL for any row that is not overdue) and `not_followed_up` (overdue and due-soon rows with no follow-up recorded in `not_followed_up_days`, by default the installation's "due soon" window) — one grouped statement. Each number has the filter that lists exactly its rows: `state` + `severity`, `overdue_band`, `no_follow_up_days`. `components/remediation/RemediationInsights.tsx` draws them above the list on both pages — a severity × (overdue, due soon) table, the lateness bands and a "not being chased" count, each number opening its rows. In the list one "Deadline" column replaces the earlier State and Due columns. "Copy summary" and a CSV of the filtered rows are built in the browser (`utils/remediation` `remediationSummary` / `remediationCsv`, saved through `utils/download.saveBlob`): the page asks `GET /remediation/export` (cross-project: `/remediation-overview/export`) ONCE — `remediation_service.export_rows`, the list's own function without its count statements, up to `EXPORT_MAX_ROWS` (20,000) with the true `total`, so beyond it the page says to narrow the list — and builds the file itself, formula-escaping the cells: the words of the CSV are the page's, so the server sends rows, not a file (v2.475.0 / 5.359.0; it was the list read 200 rows at a time). The dialogs default their dates to the server's day (`as_of`), not the browser's.

**Teams (v2.462.0).** `finding_host_remediation.team` is the group that owns the fix — free text, at most 100 characters, compared without case. A contact is a person; the team is how a manager reads the backlog. It is a tracked field like the others: set, replaced (a conflict without `overwrite`) or cleared through `apply`, and logged on the host's timeline. `remediation_service.teams` returns each team's rows by state, the most overdue first, with a last entry `team: null` for the rows that have a contact and no team; the list takes `team=` and `group=team`. Routes `GET /remediation/teams` on every mount (MCP `remediation_teams`); the page's "By team" view.

**History (v2.462.0).** A deadline is derived from the current timeline and the finding's current severity, so yesterday's states cannot be recomputed honestly. `remediation_daily` (`RemediationDaily`, revision `c6f3d1a8e5b7`; unique on project + day) therefore holds one row per project per day with its findings on hosts by deadline state, written by `remediation_service.snapshot` from the worker's remediation sweep (below): the day's rows are upserted on every run (two workers may sweep at once), so each ends the day holding that day's last count; a project with no rows gets none; nothing is written while the feature is off; and nothing is ever back-filled. `trend` (`GET /remediation/trend?days=`, 7–730, default 90; MCP `remediation_trend`) returns `daily` — the recorded days summed over the projects asked for, an unrecorded day absent rather than zero — and `closed_by_month` — the closed rows of exactly the last twelve calendar months (the current one included) as `on_time` / `late` / `no_deadline`, grouped in SQL from the rows' own `closed_on` and `closed_due_on`, not from the daily table. `components/remediation/RemediationTrend.tsx` is the "Over time" section of both pages (Observable Plot, imported in the component: overdue per recorded day, closed on time and closed late per month, with a table view).

**A contact's list as a document (v2.463.0).** `remediation_report.build_dataset` calls `ClientReportService.build` on a transient `Report` (so the finding references, written text and placed images are the client report's), keeps the findings and systems assigned to the contact that are still open, renumbers the data paths, and adds each system's deadline. It prints only what that contact may see: a finding's confirmations for the contact's own systems only; an image that is not placed in the text is withheld unless every system of the finding is the contact's (the job's status reports `images_withheld`, and the dialog says how many); a finding that has no issued number prints no F-number. `report-templates/contact-report` (`REMEDIATION_REPORT_TEMPLATE`) extends the penetration test template (`"extends": "pentest"`, §8): it holds only `report.qmd` and the `_finding.qmd` / `_affected.qmd` partials and takes everything else from `pentest`, except branding, which is its own. It is a template of `kind: contact` (`report_template_service`: `list_templates()` returns client templates only; `client_template()` guards every client-report entry point), filled and rendered by the same `quarto_render` and held to the same hostile-text test. The job (`report_type='remediation'`) is dispatched by `client_report_render.run_client_job`; `report_job_service.PAGE_OWNED_REPORT_TYPES` keeps it out of the inventory downloads list and sends no "report ready" notification — `RemediationContactReportDialog` polls it. When the job COMPLETES (`remediation_report.record_prepared`), a `report` timeline entry (`d7a4e2b9f6c8`) is written on each host the document lists — not at queueing, and not on hosts it left out. The downloaded file's name is ASCII (`client_report_render.file_slug`).

**Alerts.** `remediation_alerts.sweep` runs from the ingestion worker's periodic tasks (`worker.py` `_remediation_alerts`, at most every 15 minutes — the same task then calls `remediation_service.snapshot` and commits both together) and writes in-app notifications (`type: "remediation"`, `source_type` `remediation_due_soon` / `remediation_overdue`, `source_id` = the project id) to the project's admins and the global admins when rows enter the due-soon window and when they become overdue. Each row remembers the deadline it was alerted for (`due_soon_alerted_for`, `overdue_alerted_for`), so a deadline alerts once per kind and a moved deadline alerts again (the sweep stamps them with one UPDATE per kind and deadline); one notification per recipient, project and kind per sweep, carrying the count and naming the worst rows (up to three as "<finding> on <address>", then "and N more"). A third kind (v2.468.0), `remediation_deferral_review`, is raised when deferred rows reach `deferred_review_on`, once per review date (`deferral_alerted_for`). No email, no webhook. `utils/notificationLinks.ts` decides the link from `source_type` and `source_id`: the list of that state — or of deferrals due for review — in that project.

**Managing due dates (v2.468.0).** Still ONE definition, in `remediation_policy.py`: `policy_due_expr` is what the policy alone gives (assigned date + days for the severity) and `due_expr` is `coalesce(due_override_on, policy_due_expr)` — the deadline in force — so the state, the list, the alerts, the breakdowns and the freeze at close all follow a date set by hand without a second rule; `state_expr` lets a row with an override skip `no_deadline` / `not_assigned`. `flag_exprs` holds the two flags (`deferral_review_due`, `deadline_overridden`), counted in the list's existing state-count statement (the list is still three statements). `_decide` decides status together with the two dates that belong to one (`closed_on` with `closed`, `deferred_review_on` with `deferred`) and refuses a deferral without its review date and note, or a hand-set deadline without a note — in the plan, so nothing of the call is written. `assign_from_report` reads what an issued report told the client from its frozen `reported` map (`client_report_service.told_by_report`: finding id + host id + DNS-name id; an addendum = what it added to its baseline) and composes `apply` in batches inside the caller's transaction. `preview_policy` evaluates `state_expr` twice — stored and proposed values — in one grouped statement over every project and writes nothing. `severity_changed` (called by `PATCH /findings/{id}`) is one `INSERT … SELECT` into `remediation_events` for the rows whose deadline is the policy's. `follow_up` takes `upcoming_days` and groups its message by project; `record_follow_up_across` records it in every project the caller administers, locking all the rows in the writers' one order.

**Oversight.** `summary.remediation` and each row's `remediation` (`null` when the installation has the feature off) carry open / closed / deferred, the open rows by deadline state, `longest_overdue_days`, the overdue rows by severity (`overdue_critical` … `overdue_info`) and by lateness (`overdue_age_1_7`, `overdue_age_8_30`, `overdue_age_31_90`, `overdue_age_90_plus` — v2.462.0, `overdue_breakdown_by_project`, the list's own expressions as flat keys so projects add up), `avg_days_to_close` over `closed_measured` rows, and `closed_late` out of `closed_with_deadline` (`remediation_service.state_counts_by_project` and `durations_by_project` — the page's own counts), and the two record / assessment gaps `reported_fixed_not_retested` and `remediated_record_open` (`verification_counts_by_project`: the list's rows and `remediation_policy.verification_expr`, so each equals the list `?verification=` opens; the strip links each to `/remediation-deadlines?verification=…`); the summary adds the installation's `days` and `due_soon_days`. The page shows them as a "Remediation deadlines" measures strip that links to `/remediation-deadlines`; the per-project remediation table that Oversight had now lives on that page.

**A person adds a test by hand (5.324.0).** *Add test* in the Tests section and *Add a test* on an open weakness open one side panel (`AddTestPanel`, rendered once by `hostTestsController`) that posts a single test to the same `POST /projects/{id}/host-tests` an agent proposes through — no second route. From a weakness it sends that row's `vulnerability_id`, defaults the priority to its severity and, when no reason is typed, gives the weakness as the rationale.

**Replays and revisions (v2.445.1).** `record_result` leaves replay validation to `record_evidence` (`server_timed=True` keeps the server's clock out of the fingerprint): the same result under a key returns the stored record, a changed one is a 409. It always runs the revision-conditional UPDATE, so a result that leaves the status unchanged still consumes the revision. `update_test` validates the state the row will have (a finished test cannot lose its only explanation). The routes serialize before `commit()` — the session expires on commit, and reading each row's id afterwards was one SELECT per test. In the browser the host's panels are keyed by the host (5.344.0): `HostInspector`, `HostFindingsCard` and the standalone `HostTestsSection` render their body with `key={hostId}`, so stepping to another host remounts them and a completion for the previous host has no state to land in. Since v5.351.0 the host's tests are ONE query (`['listHostTests', {host_id}]`, owned by `hostTestsController`), so an answer belongs to its host by its key; the keyed remount is for LOCAL state (an open panel, a draft). "Only while the reader is still on this host" after a save is the callback given to `mutate(…, { onSuccess })`; `hooks/useIsMounted` and the per-save host check (`isCurrentHost`) are gone.

**A person works a test on its row (v2.443.0).** The Tests section's one primary action, *Record result*, calls `POST /projects/{id}/host-tests/{test_id}/result` (`host_test_service.record_result`): it writes the same evidence record through `agent_evidence_service.record_evidence` (attributed to the user, no session) and moves the test in the same transaction — `finding` / `no_finding` close it, `inconclusive` / `failed` leave it in progress. Under a record whose outcome is `finding`, *Create finding* calls `POST /projects/{id}/evidence/{id}/finding` (`agent_evidence_service.create_finding_from_evidence` → `FindingService.create_finding`, the record row locked), which attaches the record's host and links the record to the finding. An agent's finding stays a proposal (§5.7); only a person's click creates one directly.

**A test can belong to a weakness (v2.445.0 / 5.322.0).** `host_tests.issue_key` / `issue_title` (migration `a9c3e7f1b248`) are set at proposal from `vulnerability_id` (`host_test_service.resolve_issue` — the observation must be on the same host) and hold the ISSUE's identity (`vuln_identity`), not the row id, so a re-scan that replaces the row keeps the link. Two things follow, and together they make one promotion path instead of two: (1) *Promote to finding* under a linked test's result calls the same `promote_or_dismiss_vulnerability(scope="host")` the weakness row's button calls — it joins the issue's finding (`dedup_key`) rather than creating a parallel one; an unlinked test still creates a finding from a title and severity. (2) Promoting the observation links that issue's `finding`-outcome evidence to the finding on every host the promotion attaches — this host for a host-scoped promotion, every host carrying the issue for an issue-wide or bulk one. Both steps are inside `FindingService.promote_vulnerability(..., host_ids=None, on_join="set"|"confirm"|"keep") -> (finding, created)`: it locks the issue's evidence (`agent_evidence_service.lock_issue_evidence`) BEFORE it looks up or inserts the finding — the one lock order of every path that makes an issue's finding — and links it afterwards (`link_issue_evidence`), unless the call is a false-positive dismissal. `on_join` says what happens to a finding the issue already has: `"set"` takes the status the person chose (the click, an accepted proposal), `"confirm"` only moves open / retest → confirmed (a test's result), `"keep"` joins it as it stands (the bulk promotion). A host-scoped promotion also reopens that host's endpoint if it had been dismissed as a false positive (`reopen_false_positive_endpoints`); an issue-wide or bulk promotion leaves every host's own dismissal alone. On the page the host's tests are loaded ONCE (`host-inspector/hostTestsController.tsx`; context in `hostTestsContext.ts`, which has no API-client import) and read by both the Weaknesses rows (`VulnerabilityGroup`: a closed row says where its tests stand, an open one lists them with *Record result* and *Ask agent to propose a test*) and the Tests section. A result is recorded in one side panel owned by the controller. The Evidence section lists only records that answer no test (`GET /evidence?unlinked=true`, "Other evidence"); a test's records are under the test.

BlueStick cannot enforce the command rules (commands run on the operator's machine; the client's sandbox is what holds), which is what `GET /.well-known/networkmapper.json` publishes: `command_approval: "operator_driven"`, `command_approval_enforced_by: "agent_and_client_sandbox"`, beside the properties the server DOES enforce (it executes nothing; a key's authority is its operator's project role; keys are session-bound, time-limited and audited). The one read-back is the session prompt's (`agent_policy.render_read_back`): project, operator, scope and working directory.

**`POST /agent/feedback`** takes friction notes, API critiques and tool suggestions at the moment they happen; `source` is `assist`, `reconnaissance` or `testing`. Rows land in `agent_feedback` with `status='new'`; a human triages via the admin-only `/api/v1/feedback/...` surface.

The endpoint shapes and the working rules are in the agent guide, **`documentation/AGENT_GUIDE.md`**, which agents fetch via `GET /api/v1/agents-guide` (optionally `?workflow=testing|reconnaissance|assist`). The guide uses HTML-comment section markers (`<!-- agents:section tags="..." -->`) so a single source file can emit workflow-scoped slices.

**BlueStick does not direct the agent's work.** It records nothing about the operator's machine and recommends no scan sequence. Which tools the operator has and which command fits their machine is the agent's and operator's business. The server keeps the tool registry (a catalogue: `reference` / `suggested` / `rejected`, `ingestible`) and `tool_output_contract` (the upload extensions each parseable tool's output must carry, which the Tool Reference commands and the upload-format docs are checked against).

**Attribution (v2.434.0).** An `AgentSession` records who did the work from three sources (`agent_session_service`): the **client** (`generated_by_tool`) from the MCP `initialize` handshake's `clientInfo` name + version when the handshake carries a live key (`record_mcp_client`, called by `mcp_assist.py`), else from the first authenticated call's `User-Agent` (`deps.py`, written once; the handshake overwrites it); the **prompt version**, set by the server at session start and resume; and the **model** (`generated_by_model`), the agent's optional self-report `agent_model` on `POST /agent/host-tests`, `POST /agent/evidence`, the proposal routes and `POST /agent/session/end` (`note_agent_model` — the session keeps the last one). A host test and an evidence record snapshot the attribution when they are written.

### 5.3 Agent API call audit log (v2.24.0)

A Starlette middleware (`app/services/agent_api_log_service.py`) wraps every `/api/v1/agent/*` request. After the response is sent (so the agent's loop is never blocked), it writes one row to `agent_api_calls` capturing: method, full path + path template, path params, query params, status code, response size, duration, source IP, user agent, API key prefix (never the raw key). For mutations, a JSON-safe body summary is stored (8 KiB cap, multipart skipped, sensitive-shaped fields stripped as defence-in-depth).

The middleware extracts referenced `host_ids` / `target_ips` from path + query + body (`referenced_entry_ids` — test-plan entry ids — was dropped by `f5c2a0d7b4e6`, test plans having gone in v2.442.0) so "did the agent query the right hosts?" is a one-indexed-query answer. Each row names its session in ONE column, `agent_session_id` (v2.449.0 — `assist_session_id` was folded into it by `b8e2a5c7d1f3`; `idx_agent_api_call_session_created` serves the per-session feed and counts). Surfaced via `GET /api/v1/projects/{id}/agent-sessions/{session_id}/api-activity` (JWT-authenticated — the agent cannot read its own audit log) and the `AgentActivityLog` component on each agent session's page (`/agent-sessions/{id}`).

Retention: the API runs a daily loop (`startup.agent_api_call_retention_loop`) that purges `agent_api_calls` rows older than `AGENT_API_CALL_RETENTION_DAYS` (default 90; ≤0 disables) and, only when `AUDIT_LOG_RETENTION_DAYS` is set (default 0 = keep forever), old `audit_logs` rows.

### 5.5 Assist (Workflow E — query the project)

For the senior-tester case where the operator just wants to *query* a project — "which hosts expose FTP?", "summarize my critical findings", "what did the last recon turn up?" (v2.64.0). Assist is the DEFAULT surface of every session.

1. **`POST /projects/{id}/assist/start`** (JWT user, `assist.py`) — the one session start since v2.433.0 — mints the project session and returns the key plus the agent prompt. It requires only `auditor` (lowered from `analyst` in v2.308.0 — safe because a key carries its operator's permissions). Sessions are listed and ended from the project's agent-sessions surface.
2. The agent reads through `/agent/assist/*` (`agent_assist.py`): context, hosts (list / count / detail / vulnerabilities / notes / web interfaces), findings, posture, patterns, segments, coverage, vocabulary, names, scans, ingestion issues, plus the NDJSON downloads (`hosts.ndjson`, `report-context.ndjson`); and, since v2.428.0, what the other pages show — the Operations workbench (the operator's own queue and reviews; no project-wide measures since v2.451.0), the untouched queue and terrain, Evidence gaps and scan compare (`agent_assist_operations.py`), scanner observations by issue and client reports (`agent_assist_reporting.py`). **Each agent read wraps the service its page uses** (`workbench_service`, `scan_diff_service`, `host_detail_service`, `scanner_observation_service`, `client_report_service`…), so an agent and a page cannot disagree on a number; read roles equal the page's, each declared on its route with `agent_read_floor(...)` (§2.2) and pinned both ways by `test_agent_role_route_matrix.py`. The host reads use the Hosts page's own filter, `host_query.build_filtered_host_query`, so a discrete filter word means what it means on the page (`search` is the search box; critical + high is critical OR high; `ports` with `services` must be met by one open port) and the same host query DSL drives `q=`. A discrete value that cannot be understood is a 422 naming it on both doors (`host_query.parse_port_list` / `parse_id_list`); the agent door also refuses an unknown `state`, a `subnets` value that is not a network or an address, and a list that names nothing (`agent_common.check_host_filters`).
3. **Reads need project membership; bulk exports need `auditor`; writes are whatever the operator's role allows.** An analyst's session can write notes, review status and hostname/OS corrections; an auditor's or viewer's cannot, because its operator cannot. Nothing narrows writes to "assigned" hosts. An agent cannot triage (promote or dismiss) a finding or change its report text under any role — it PROPOSES (see §5.7).
4. **Managed and reviewable from one page per session** (v2.432.0 / 5.312.0). Agent Sessions (`/agent-activity`) leads with the live sessions — each with its key state, last call, its work (`host_test_count` / `evidence_count` on the row, two grouped queries in `agent_session_service._attach_work_counts`) and Resume / End — then the history. `/agent-sessions/{id}` adds the tests the session proposed (`GET /host-tests?agent_session_id=`), the notes the agent wrote (`GET /agent-sessions/{id}/notes`) and the per-session API-call feed (`GET /agent-sessions/{id}/api-activity`). End / Resume rights come from the row (`can_end` / `can_resume`, the rules the routes enforce), never from the global role. The row reports the STORED status beside `key_expires_at` and `renewable_until`: an active session whose key has run out is resumable, not ended, until the hourly sweep (`lapse_expired_agent_sessions`) lapses it past its lifetime; "which of my sessions can an agent use now" is the key's expiry (`utils/agentRuns.hasLiveKey`, used by the start dialog's panel and `useAgentTask`).
5. **One table, one id** (v2.449.0 / 5.328.0, review 2026-10-01 B3). A session is one `agent_sessions` row and its id is the only one: `POST /assist/start` writes that row and nothing else, every route is `/projects/{id}/agent-sessions/{id}/…`, and `agent_api_calls` / `agent_feedback` name their session in `agent_session_id` alone. Until then each start also wrote an `assist_sessions` "pointer" row whose id the review routes, the notes and the call feed were keyed by — two ids per session, two route families, id translation in three places, and a second key-expiry helper (`assist_session_service`, folded into `agent_session_service`). Migration `b8e2a5c7d1f3` moved what only the pointer row carried onto its session, gave a session to any pointer row that had none, re-keyed calls and feedback, and dropped the table. `agent_sessions.legacy_assist_session_id` keeps the old id for one purpose: the deprecated `/assist-sessions/{old_id}…` and `/assist/sessions/{old_id}…` routes (and the SPA's `/assist-sessions/:id` redirect) find the session an old link or bookmark meant. Those routes resolve an id as a legacy id first and, when no session in the project has it, as the session's own id (`agent_session_service`'s one resolver) — the start response still returns `assist_session_id` (equal to the session id) and a tab loaded before the upgrade sends it there; where two old rows pointed at one session, the session kept the LOWEST old id, so the other old link no longer resolves to it. A legacy `assist` session is the same kind of row, so it has the same page.

### 5.6 MCP transport (Workflow F — all of the above, as tools)

Every workflow above is also reachable over the **Model Context Protocol** at `POST /api/v1/mcp` (`mcp_assist.py` for the transport, `mcp_tools.py` for the declarative registry). A `tools/call` loops back into the same `/agent/*` endpoint **in-process** via an ASGI transport, forwarding the caller's `X-API-Key`, so auth, the operator-role check, row scope, and the audit log run unchanged — the MCP layer makes no authorization decision of its own. A registry entry authors only what the endpoint cannot say (description, method, path, per-argument descriptions or narrowing, hidden parameters, MCP-side defaults, write flags); which arguments exist, where each is sent, their types, enums, bounds and required-ness are derived from the route's OpenAPI operation, once per backend worker just after startup (`main._warm_mcp_registry`; on first use otherwise) (`mcp_tools.derive_tool`), so a new endpoint parameter is offered by its tool without a registry edit.

`tools/list` returns the WHOLE catalogue to every session (`GET /references/mcp-tools` is the live list and count — no number is kept in the docs; the per-workflow filter went with the per-workflow keys in v2.337.0). Listing was always presentation rather than authorisation — the endpoint behind a tool decides on every call. Bulk, file-shaped endpoints (NDJSON streams, target lists, `POST /agent/uploads`) are deliberately *not* tools.

See [MCP.md](MCP.md) for the transport details, the certificate (local root CA + fingerprint check), the tool catalogue, and the guardrail model.

### 5.7 Evidence records and proposals (v2.436.0)

The rule: an agent's change is a **proposal** when it alters what the team has concluded or what the client report says; everything else it writes is direct and attributed to its session.

- **Evidence records** (`evidence_records`, `agent_evidence_service`; `POST /agent/evidence`) are direct and immutable: host, optional finding / endpoint, tool, command, outcome, summary, session + model + client. Raw output is kept in the row (`raw_output`: Text, deferred so a list never loads it, 5 MB cap, NUL removed) with a 2,000-character preview. Until 2.439.0 it was a file under `uploads/evidence/<project>/`, which a host or project deletion left behind. The migration `e3a7c1d9f5b2` read those files into the rows and left them on disk to be removed by hand. A record may name the host test it answers (`host_test_id`, with a `request_key` that makes a retry return the stored record), or stand alone — this is how ad-hoc agent work leaves an audit trail. Records with outcome `finding`, `no_finding` or `inconclusive` are what make a host *tested* (§5.1).
- **Proposals** (`agent_proposals`, `proposal_service`; `POST /agent/proposals/*`) have five kinds: `finding_text` (one row per report field), `finding_create`, `observation_promote`, `observation_dismiss`, `endpoint_status`. Each keeps its payload, rationale, cited evidence ids and attribution (`source` agent | llm_draft, session, model, client, prompt version).
- **Accepting runs the same code as the click** (`finding_actions.py`: `apply_report_text`, `promote_or_dismiss_vulnerability`; `FindingService.create_finding` / `set_endpoint_status`) as the person accepting, inside a savepoint. So the authored-content rule decides who may accept report text, and a refusal leaves the proposal pending with the reason in `error` (not for a 403, which is about the caller). Accepting a field's text supersedes that field's other pending proposals; several stand side by side until then, so output from different models can be compared. A bulk accept never chooses between them (`competing_drafts`). Deciding goes through `proposal_service.lock_for_decision`: for report text it locks the FINDING first, then the proposal row (`get_proposal(for_update=True)`, `populate_existing`), so two concurrent accepts apply it once and two reviewers accepting different drafts of one field end as one accept and one 409 (locking the proposal first deadlocked: each held its own proposal and waited for the other's). The page's bulk actions send at most 200 ids (`PROPOSAL_BULK_MAX`, pinned to the route's limit) and say so when more are shown. An accepted `cvss_vector` clears the score: a 3.x vector recomputes it, a 4.0 one leaves it for the analyst, because the old score belonged to the old vector.
- **"Needs review"** is one definition (`proposal_service._about_findings` / `pending_per_finding`): the proposals naming a finding, plus promote/dismiss proposals on a scanner observation that evidences it (`finding_vulnerabilities`). It is derived, never stamped, because the link can change. The finding page's proposals and the report's pending warning both read it.
- Reviewer routes are project-scoped (`proposals.py`: list, summary, accept, reject, bulk; evidence reads); agent routes are in `agent_proposals.py`.
- **How a section is to be written is the installation's, in one place** (v2.469.0): `services/report_writing_guidance.py` (table `report_writing_guidance`, one row per key — `general` and each section; no row is the shipped default) is read by both drafting doors. The in-app drafter's system prompt is `drafter_system_prompt(load(db))`; an agent reads `for_agents(load(db))` as `writing_guidance` on `GET /agent/assist/findings/{id}`, and alone at `GET /agent/assist/writing-guidance` (v2.470.0: a new finding has no finding read). A global admin edits it in System settings (`GET` / `PUT /report-writing-guidance`, audited). `FIXED_RULES` — nothing the data does not support, decline rather than guess, no record named, a complete section — are code, come after the guidance in the prompt and are stated to take precedence; a change of guidance needs no prompt version and no rebuild.
- **The in-app drafter is the same path** (v2.437.0): "Draft empty sections" (`POST /reports/draft/finding-text`) creates `finding_text` proposals with `source: llm_draft` and the provider's model — one review path, one UI. Since 2.455.0 the model answers `null` + a `missing` reason for a section the data does not support (`report_draft_service.parse_finding_text_answer`): no proposal, the reason in `declined` and the drafts' rationale, shown beside the section — never report text. Agents are told the same ("not enough to write this" is a valid answer; guide, session prompt, `propose_finding_text` / `propose_finding`).
- **Provenance** (`proposal_service._provenance`, 2.439.1): an accepted change names the proposal it came from on the history row the change itself writes. That is the creation row (`create_finding(summary=)`), the endpoint row (`set_endpoint_status(note=)`) or the promote/dismiss summary, and for report text (which has no history otherwise) one same-status row: "Impact set from agent proposal #N (model, agent session #S)", or "from AI draft #N". "My activity" shows a same-status history row's summary instead of "Marked … <status>".
- **Notifications** (`proposal_service._notify_finding_people`): the finding's author and owner, one unread notification per person per agent session, updated in place, and computed once per request rather than per proposal. **What a person is shown matches what they were told** (2.440.0): `proposal_service.findings_of` (authored or owned) through `_about_findings` scopes the list (`mine`), the summary (`pending_mine`), the notification's link (`scope=mine`) and the top-bar count. A project admin sees everyone's by default.
- **Report text is a rewrite** (2.440.0): accepting replaces the section with the proposed value, so the agent is told (MCP `propose_finding_text`, the guide, the "Work on this with your agent" task) to send the complete new section, report-ready, with the critique in `rationale`. **Report issue** warns (never blocks) on pending proposals for reported findings and on images from agent-written notes (`client_report_service` summary).
- **Report text is for a reader who has never seen BlueStick** (2.467.0): `report_text.internal_references` is the ONE definition of a phrase that names a BlueStick record ("Finding #277", "evidence record 57", "host #12") or BlueStick itself, code spans and fenced blocks excluded. Three readers: `proposal_service` refuses such a section at propose (422, both `finding_text` and a new finding's `report_text`); the in-app drafter declines the section with that reason; and a report's `summary.internal_references` lists the reported findings whose written text still holds one (a warning on the draft's page, never a block — text a person saves is not refused).
- **UI** (v5.316.0): the Proposals page (`/proposals`, Agents hub; pending by kind, filters, bulk accept/reject); on the finding page (5.334.0) each proposal is reviewed where it applies — report-text drafts inside their Report text section, the current text beside the selected draft (lettered A, B…; `FieldDraftsReview` / `TextComparison`, with a word-level "Changes" view and a warning when the field changed after the draft was written, from the proposal's server-recorded `base_value`), endpoint changes on their row in `FindingEndpoints` — under a "Proposals to review" summary at the top of the page, read once by `hooks/useFindingProposals`; accept, accept and edit (from the draft or the current text), reject with an optional reason — `decision_note`, which the proposing agent reads back through `list_proposals` — all through `hooks/useProposalDecision`; agent evidence on the host inspector; a pending count in the top bar (hidden at zero); "Work on this with your agent" in the finding's Report text section (5.317.0), which hands the operator's agent session a review task (`agentInstruction.reviewFinding`) whose output comes back as proposals. All share `components/proposals/ProposalItem.tsx`.

## 6. Security model

Security work landed across v2.9.5, v2.9.7, and v2.9.8. The below is the current state; see CHANGELOG for the audit trail.

- **JWT signing + Fernet credential encryption** use **separate keys** by design. `settings.SECRET_KEY` signs JWTs; `settings.CREDENTIAL_ENCRYPTION_KEY` derives a Fernet key via HKDF for LLM provider + integration credential encryption at rest. A compatibility fallback to `SECRET_KEY` exists when `CREDENTIAL_ENCRYPTION_KEY` is unset (logged once as a deprecation warning); the fallback will be hard-removed in a future major.
- **SSRF protection** is two-layered. `require_public_http_url()` validates user-supplied `base_url` values at save time — parses the URL, enforces `http`/`https` scheme, resolves the hostname via `getaddrinfo`, and rejects every resolved IP in RFC1918, CGNAT, loopback, link-local (including `169.254.169.254`), and IPv6 equivalents. On top of that, `safe_http_client(allow_private=...)` returns an `httpx.Client` with a custom `HTTPTransport` that **re-resolves and re-validates** every outbound hostname at connect time, closing the DNS-rebinding TOCTOU window the plain validator leaves open. Redirects are disabled so a 302 can't land on a private IP. Ollama is the sole integration type with `allow_private=True` because users legitimately run it on localhost.
- **XXE protection** — three coverage strategies depending on parser:
  - `nessus_parser.py` uses `defusedxml.ElementTree` for parser entry points (`parse`, `iterparse`, `fromstring`) which disables entity expansion, external DTD fetching, and entity references at parse time. Type annotations still reference `xml.etree.ElementTree.Element` because defusedxml only wraps the parser — not the element tree.
  - `nmap_parser.py`, `masscan_parser.py` and `openvas_parser.py` stream with lxml through `xml_stream_helpers.iterparse_safe`, which sets `resolve_entities=False, no_network=True, huge_tree=False` in one place (v2.41.0). lxml is kept because `defusedxml.lxml` is deprecated upstream as of 0.7.1; the explicit flags defeat billion-laughs entity expansion, SYSTEM-entity local-file disclosure, and the huge-tree memory exhaustion vector.
  - All other parsers ingest JSON / CSV / text and don't construct XML at all.
- **Decompression-bomb caps** — `eyewitness_parser.py` enforces per-file (50 MB), running-total (500 MB), and entry-count (5000) caps on uploaded EyeWitness ZIPs (v2.41.0). The streaming extractor counts bytes on the way out and aborts + unlinks the partial file if either cap is exceeded mid-stream, so a spoofed central-directory `uncompressed_size` field can't defeat the check.
- **Streaming JSON for large BloodHound exports** — `bloodhound_parser.py` switches from `json.load` to `ijson.items` for files ≥50 MB (v2.41.0). The structure is auto-detected by peeking the first 64 KB (top-level array vs `{data: [...]}` vs `{computers: [...]}`); files below the threshold keep the fast `json.load` path.
- **Login rate limiting** — three limits, all counted from `audit_logs` (`core/security.py`; no column on `users` — `failed_login_attempts` / `locked_until` were dropped by `a0d7b5e2c9f1`). `login_lockout_active()`: 5 failed sign-ins for one username from one client address within 30 minutes, counted since that address last got the password right, lock THAT address out of that account (HTTP 429) — the account's owner still signs in from anywhere else, so guessing cannot lock a person out. `login_throttle_exceeded()`: ≥20 failures from one address across usernames, or ≥100 for one username across addresses, in 15 minutes → 429 (the per-username ceiling is deliberately far above the per-address limit, because while it holds the owner is kept out too). The 2FA step has its own per-username limit (10) counted over wrong codes only. The client address is the peer nginx saw (it overwrites `X-Forwarded-For`), and the answer is decided by the username as typed, so it says nothing about which accounts exist.
- **Username-enumeration timing** — `authenticate_user()` (v2.41.0) calls `pwd_context.verify(password, _DUMMY_PASSWORD_HASH)` in the unknown-user and inactive-user branches so every path pays the same bcrypt cost. The pre-fix timing channel (5 ms unknown vs 80 ms known) is closed.
- **Prompt sanitization** — `backend/app/services/prompt_sanitizer.py` strips `X-API-Key: nm_agent_...` lines, redacts credential bullets (Access key / Secret key / Password / Username / API key / PDCP token / Secret), and catches bare `nm_agent_` tokens of 20+ chars. The `/llm-providers/{id}/complete` endpoint calls it before forwarding. (Its client-side twin `utils/promptSanitizer.ts` was deleted with the in-app agent panel in 5.313.0.) Changing bullet labels in `agent_prompt_service._integration_block` requires updating the sanitizer in lockstep.
- **File upload validation** — `ingestion_service` enforces a max chunk-by-chunk size during streaming, slugifies filenames, and runs a magic-byte check after write (`.xml`/`.nessus` must start with `<`, `.json` with `{` or `[`, `.gnmap` with `#` or `Host:`, text files must not contain NUL bytes).
- **Pydantic `max_length` caps** on high-risk write schemas: AnnotationBase.body 16 KB, SubnetBase.description 1 KB, ScopeBase.name 256, and the host-test schemas (`host_test_schemas.py`: tool 100, description / command / rationale / expected result / tester summary 10,000 each, dismissal reason 2,000, label 255, at most 20 HTTP(S) references of ≤2,048 characters, at most 200 tests per batch; unknown fields and NUL are refused).
- **CORS** — origins restricted to configured values (`settings.CORS_ORIGINS`); never `*`. Deploy script regenerates `.env` with the detected host IP.
- **HTTPS** — production deployments terminate TLS at the Nginx frontend container using self-signed certs by default (`scripts/deploy.sh` generates them during first-time setup). Security headers are set in `ssl-nginx.conf`.

## 8. Observability, operations, and recovery

- **Structured logs** — backend + workers log to stdout via `logging.basicConfig`. `scripts/collect-logs.sh` produces an anonymised bundle, safe to share, covering the backend, worker, report-worker, nginx and db logs, the ingestion queue, and a per-format parser audit. The parser audit holds field-coverage counts only. `scripts/scrub_logs.py` rewrites every file:
  - Values harvested from the database and `.env` become stable pseudonyms.
  - So does anything shaped like an address, name, URL, account or secret.
  - SQL error row data is removed.
  - If scrubbing fails, no bundle is written.
- **Request timing, with the SQL in it (2026-10-01)** — `core/request_context.py` writes one `app.access` line per request and a `SLOW request` warning at or above `SLOW_REQUEST_MS` (default 1000). Both end with `db_ms=` (time spent inside database statements), `db_n=` (how many statements) and `route=` (the route TEMPLATE, `/api/v1/projects/{project_id}/hosts/`, so every project's requests to one endpoint group together; `-` when no route matched): `GET /api/v1/projects/7/hosts/ -> 200 412ms req=… db_ms=371 db_n=34 route=/api/v1/projects/{project_id}/hosts/`. `duration − db_ms` is Python. The response's `Server-Timing` header carries the same split (`app;dur=…, db;dur=…`) for the browser's Network tab. The counters are two SQLAlchemy cursor hooks on the engine (`instrument_engine`, attached in `db/session.py`) writing to a per-request object in a contextvar; outside a request — the ingestion and report workers, startup tasks, scripts — they record nothing. A statement that fails or is cancelled is counted too.
- **API statement timeout (2026-10-01)** — `API_STATEMENT_TIMEOUT_MS` (default 30000, 0 = off) is the longest any single statement of an API REQUEST may run. `db/session.py`'s `get_db` applies it to the request's own session — `SET LOCAL statement_timeout` at the start of each transaction that session opens — so it covers the whole request and never outlives it: the pooled connection goes back without it. It is deliberately not an engine or connection default, because the ingestion worker, the report worker, startup tasks, the seed / repair scripts and Alembic share the module and the environment (`env_file: .env`) and run long statements by design; they open `SessionLocal()` themselves and are never limited. A statement that exceeds it is cancelled by Postgres (SQLSTATE 57014), the request answers **503** with a plain message, and its connection is freed instead of being held until the client gives up — a few slow aggregations at once used to exhaust a worker's pool and fail `/ready` with it. A request path that runs long on purpose (a streamed export) calls `disable_statement_timeout(db)`; `is_statement_timeout(exc)` recognises the cancellation.
- **Unfiltered Hosts facets are cached per worker (2026-10-01)** — `/hosts/filters/data` keeps the scan-derived facets (port / service / OS / technology / RDAP / weakness / check counts) of the UNFILTERED page for `HOST_FACET_CACHE_SECONDS` (default 30, 0 = off), the same per-worker TTL pattern as `/posture`. Tags, subnet labels, subnets, sites and the scan list are read on every request. A filtered request is never cached; it evaluates the filter once, fetches the matching host ids and passes them to each facet statement as one array parameter.
- **Audit trail** — `audit_logs` captures login/logout, password change, role change, session revoke, upload, scan delete, and other security-relevant events with user_id + IP + user agent. Project and membership changes are audited too (2026-10-01): `project_created`, `project_updated` (old and new value of each changed field), `project_archived` / `project_unarchived`, `project_deleted` (name, slug and the members with their roles — the project's own history cascades with it) and `project_member_added` / `project_member_role_changed` / `project_member_removed` (the role before and after). Each row is staged in the same transaction as the change (`log_audit_event(..., commit=False)`), carries the project id as `resource_id`, and a refused change writes nothing.
- **Data-repair ledger (2026-10-01)** — a *data repair* corrects rows that older code wrote: not a schema change (Alembic does not carry it) and not safe to run unasked at boot (one deletes rows; the other writes through the application-level vulnerability de-duplication and must not run beside a live import). `app/services/data_repair_service.py` is the list (`KNOWN_REPAIRS`: `misconfig_backfill`, `netexec_results_repair`, each with its exact command) and the table `data_repairs` (`models_data_repairs.py`; one row per repair name — when, by what, mode `apply` / `nothing_to_repair` / `not_needed`, the repair's own counts as JSON, the backend version, a run count) is the record. Each repair script records its own run in the transaction that makes the corrections, and only when the run settles the repair for the whole instance (a `--project` run does not; a NetExec dry run does when it finds nothing). The revision that creates the table marks both as `not_needed` on a database with no hosts, so a new installation is never told to run them. Nothing runs a repair automatically: `scripts/deploy.sh` (after a healthy start), `scripts/status.sh` and `scripts/data_repairs.py` print the pending ones with their commands, and `collect-logs.sh` includes the ledger (counts only).
- **Health checks** — `/health` (backend; nginx proxies it and `/ready` with 5 s timeouts and serves `/live` itself), a Docker HEALTHCHECK on `https://localhost/` (frontend), `pg_isready` (db), heartbeat-freshness checks (both workers — each rewrites its own heartbeat file every loop, so a wedged worker goes stale → unhealthy).
- **Async report pipeline** — the host inventory's JSON download and the client-report HTML/DOCX renders are generated off the request path. The API enqueues a `report_jobs` row (`ReportJobService`), the **report-worker** claims it via `SELECT … FOR UPDATE SKIP LOCKED`, builds the artifact (`report_generator.py` for the JSON, `client_report_render.py` for a client report; a row naming any other format fails with a message saying so), and writes it to the shared `uploads/report_artifacts` volume; the UI polls job status and downloads the finished file. Mirrors the ingestion pipeline (same `worker_loop.py`, same orphan-reaping semantics). See §1 for the container.
- **Client reports (Quarto, v2.379.0–2.381.0)** — the findings-first client deliverable, on its own page (`/reports`) with history and addenda. `endpoints/client_reports.py` → `client_report_service.py` decides what a report contains (confirmed / accepted-risk / remediated findings; false-positive endpoints dropped; open/retest counted, not shown), freezes it on ISSUE (project admin; numbered, `reports.snapshot` holds the dataset and the cumulative reported state) and computes an addendum's delta against the baseline's frozen state by finding AND endpoint (new findings, further systems, withdrawals, and reported findings whose SEVERITY differs from the baseline's frozen value — never by date, never a title or status change, never remediation). Rendering runs on the report worker (`client_report_render.py` → `quarto_render.py`): the template in the root `report-templates/<name>/` is filled in Jinja's sandbox with every value Markdown-escaped, written Markdown is inserted by `quarto_fields.lua` from `data.json` after Quarto's filters, and Quarto (only in the `report-worker` image target) produces HTML and DOCX (plus the Quarto source as a zip) in a throwaway directory with a clean environment. There is no PDF format (removed v2.407.0): the Word report carries the design (`reference.docx`: cover page, header/footer, page numbers) and is exported to PDF from Word; a PDF stored with a report issued earlier still downloads. `quarto_fields.lua` reads each field with a trailing newline — without one, `pandoc.read` drops a table's last row out of the table. The pentest template's Word post-processor (`scripts/fix-docx-report.py`) frames screenshots and puts the installed `logo` and `cover` (title page image) assets in place of the placeholder drawings named `bluestick-logo` / `bluestick-cover` in the shipped `reference.docx`, scaled to fit their boxes. Draft previews are ordinary expiring report jobs; an issued report's files are kept in `uploads/client_reports` with their SHA-256. A finding's report text (`findings.description` … `cvss_score`) is authored content, seeded once from the scanner row or source note; report images are opt-in (`note_attachments.include_in_report`). A template's OWN images (logo, cover art) are declared in its `template.json` under `assets` (`id`, `path` relative to the template folder, `label`, `description`, `note`, `required`, `formats`); `quarto_render.template_assets` validates each path (relative, inside the folder, image extension, a narrow charset because it is printed unescaped) and reports `present` (a regular file, no symlink — `_copy_template` skips symlinks). `GET /client-reports/templates` carries them; since v2.431.0 a global administrator may also UPLOAD a PNG / JPEG / `.docx` asset from the Reports page (`template_asset_store.py`: stored in `uploads/template_assets/<template>/`, never in the read-only template folder; the bytes validated against the asset's kind and the template's `max_bytes` / `min_width` / `min_height` / `aspect` guidance; audited). The render places an upload over the template's own file in its private copy (`quarto_render._place_overrides`, before `_apply_replacements`), and an upload is stored content-named (`<asset>.<first 16 hex of its SHA-256><ext>`) and named by its `.json` metadata. **Issuing freezes the template too:** `client_report_service.freeze_report_template` copies the template as the renderer would use it at that moment — its base's files, its own, every uploaded file in place — to `uploads/client_reports/<project>/<report>/template/<name>/` and records its digest in `snapshot["template"]`; an issued report's files are rendered from that copy (`frozen_template_dir`, digest-checked), so a logo uploaded or a template folder changed by an upgrade afterwards can neither change them nor block the render. `report_template_service.fingerprint` (the template's files, its base's, and its uploads) is still recorded on each issued report as provenance; only a report issued before the copy existed (no `snapshot["template"]`) is still checked against it and refuses to re-render with other branding. The Reports page's "Templates" section lists every installed template with its files, each with its guidance and a thumbnail (server paths, install steps and upload for global admins only), while a draft chooses its template beside the Preview buttons (saved at once) and shows its files as one line unless a required one is missing (5.286.0). A missing REQUIRED image makes preview/issue/render refuse with 409 naming `report-templates/<name>/<path>`, and the template reads one with `asset("id")` — the path when installed, else `''`, so an absent optional logo leaves the layout unchanged. Four templates ship: three client-report templates — `pentest` (the default), `executive-brief` (leadership; Word + HTML) and `remediation-worklist` (host-by-host, the minimal commented starter) — and `contact-report` (`"kind": "contact"`: one contact's remediation list, which EXTENDS `pentest`; not a client template, so no draft or project default may choose it). A template may extend another with `"extends": "<folder name>"` in `template.json` (`quarto_render.template_base` / `template_manifest` / `template_file` / `materialize`): its own files are laid over the base's and a manifest key it leaves out is the base's — never `title`, `description` or `kind` — one level only (a base extends nothing), and the base's installed images and uploads are never taken, because branding is per template; a base that is missing, is the template itself or itself extends another is a template problem; `report-templates/README.md` is the authoring guide, and a folder that cannot be offered is listed with its reason by `GET /client-reports/templates/problems` (global admins, on the Reports page) instead of vanishing.
  - **How a finding was confirmed (review 2026-10-01 B8).** A template that sets `"evidence_records": true` in `template.json` (`pentest` does; `executive-brief` and `remediation-worklist` do not) gets, on each finding, `confirmations`: its linked evidence records (`evidence_records.finding_id`) whose outcome is `finding` — tool, system, when, who (the person who recorded it or, for a record an agent wrote, the session's OPERATOR by full name — nothing about the session is printed; `by_agent` stays in the data for the report page's count), the command as run and an excerpt of the output from `raw_output_preview`. There is no per-record "in report" mark, so the outcome is the rule; only records on a system the report lists for that finding are taken (not a false-positive endpoint, not a host the finding is not attached to), at most 10 per finding (`confirmations_omitted` counts the rest), with the command cut to 600 characters and the output to 30 lines / 1,500 characters, terminal colour codes and control characters removed (`ClientReportService._confirmations`, `report_excerpt`). The list is part of the dataset, so issuing freezes it in `reports.snapshot`; it is not in `reported`, so the addendum comparison does not see it. A command line and tool output never become `.qmd` source: the template prints them with `code(c, "command")`, a placeholder `quarto_fields.lua` replaces — after Quarto's own filters — with ONE verbatim code block built from the string in `data.json`, never parsed as Markdown. The hostile-text contract test carries a hostile command and output for every shipped template. The summary's `evidence_records` / `agent_evidence_records` count what is printed and how much of it an agent recorded; a finding the template shows without its details keeps no confirmations in the dataset (see "What a report prints is measured" below).
  - **A render timeout ends the whole process group (review 2026-10-01 R14).** `quarto` is a bash launcher that runs deno without `exec`, so killing the launcher left deno and pandoc running after every timed-out render. `quarto_render._run_group` starts Quarto and the template's post-processor in their own session and, on timeout, signals the group (TERM, a short wait, KILL) and reaps it; both timeouts are a `RenderError` whose message carries no work-directory path.
  - **Images in report text.** An image attached to a finding (its comments, or its source-note thread) is ticked "In report", captioned (`note_attachments.caption`, by the uploader or an admin — the tick's rule) and may be PLACED in one of that finding's written sections with `![caption](evidence:<attachment id>)`. `services/report_images.py` is the one place the rules live: what a reference is (`REFERENCE`, read through `iter_placements`, which skips code spans and fenced blocks — an example written in code places nothing; frontend twin `utils/reportImages.ts`, `codeSpans`), which images a section may show (`report_placement`: the finding's own, ticked, printable), the refusal to delete or un-tick a placed image or the note holding it (`refuse_if_placed`, 409 naming the section), and the check on an agent's proposed section (`check_references`: 422 for an id that is not the finding's, 409 at accept for one nobody ticked). The dataset carries, per finding, `images` (all ticked), `placed` (field → the images it places) and `evidence` (the unplaced: the trailing block). `quarto_fields.lua` shows an `evidence:` image only when `placed` lists it for that field of that finding — the builder decides, the filter never trusts the text — and builds every figure (placed, or printed by the template's `image(e)`, which is a placeholder too) from `data.json`, then numbers them "Figure N: …" in document order in one pass (Jinja cannot: a placed image does not exist when the template is filled; tables are still counted by the template). A figure is a block: one in a paragraph splits it, one in a table cell follows the table. `md(…, images=False)` leaves placed images out (the executive brief). **An issued report owns its images:** `client_report_service.freeze_report_images` copies each image's bytes to `uploads/client_reports/<project>/<report>/evidence/` and records them in `report_images` (sha256) inside the issue's transaction — a missing file refuses the issue — and the issue render reads those copies (`client_report_render._issued_evidence_resolver`, hash-checked), so an attachment deleted afterwards cannot fail it. A report issued before the copies existed has no rows and reads the live attachment, as before. The copies are in the uploads backup with the rendered files, and a deleted project's `client_reports/<id>/` folder is removed with it. On the finding page `hooks/useFindingImages` loads the list once (`GET /findings/{id}/images`) for the image rows, the editor's Insert image picker and `SafeMarkdown`'s preview, which shows a known reference as the image (an object URL fetched through the attachment route) and anything else as a note or alt text. The host inventory downloads carry no images and use none of this. **One grammar, applied when a section is saved:** Markdown's other spellings of the same image (`(<evidence:57>)`, a single-quoted title, an alt text over two lines, a reference-style image) are not placements; `report_images.normalise_references` rewrites them to the one form in `finding_actions.apply_report_text` — the single write path of a person's save and an accepted proposal — and in `proposal_service` before `check_references` (propose, and the reviewer's `edited_value` at accept), so what is stored, checked, protected from deletion and printed is the same text.
  - **What a report prints is measured, not assumed (review 2026-10-01 S2).** The shipped templates differ — the brief prints no image, the worklist only those placed in the recommendation of a finding still to fix, an addendum lists an already-reported finding in one line — so `ClientReportService` fills the report's template once with its dataset (Jinja only, no Quarto run: `quarto_render.printed_parts`, which records every `md()` / `image()` / `code()` call and every `confirmations` loop) and writes the result INTO the dataset: each image gets `printed` and `printed_in`, and a finding whose confirmations the template did not read has them emptied (`evidence_records_not_printed` counts them). The summary carries `images_printed` (inside a section), `images_trailing` (the trailing block) and `images_not_printed` — the three add up to `images` — with `images_not_printed_reasons` and `template_images`; all are `null` when the template cannot be filled, and then every image counts as printed. A template's `template.json` → `images {fields, trailing}` is the author's statement of the same thing, shown before a draft exists (`GET /client-reports/templates`); tests pin declaration == fill == rendered figures for every shipped template (`report_template_service.image_declaration_problem` says how a declaration and its `.qmd` disagree; nothing checks an operator's own template at run time — the measurement, not the declaration, decides what is copied and counted). **Issuing copies, and requires the file of, PRINTED images only** (`freeze_report_images`); the agent's report read passes `printed` / `printed_in` and the same summary through.
  - **Math is off, in three layers (review 2026-10-01 S1).** Written text with `$…$` must stay text (a price range rendered as a formula, and in HTML pulled a script). (1) `quarto_fields.lua` reads each field with `gfm-raw_html-tex_math_dollars-tex_math_gfm`, so pandoc parses no math; (2) its `clean()` turns any `Math` node that arrives all the same back into the characters typed; (3) every shipped template sets `html-math-method: plain` and `quarto_render` passes `-M html-math-method:plain` on every HTML render, so a template without the line loads no math library either. Each layer is tested alone.
  - **Evidence images are looked up once (R16).** `client_report_service.finding_image_attachments` is the one query for a set of findings' attached images (own comments and the source-note thread); the client report passes `marked_only=True`; the in-app drafter's captions and `report_images.attachments_of` pass `False` (every attached image). The HTML host report, which also passed `False`, was retired. `_ledger` selects only the `reported` key of each issued snapshot.
  - **Scope cutoff (v2.441.0, `report_scope.py`).** A project with thousands of scoped networks printed a table that ran for pages. Each template's `template.json` sets `scope_inline_max` / `scope_domains_inline_max` (default 25; `null` for a template that prints no scope). `ClientReportService._scope_block` adds to the dataset's `scope`: totals (networks, IPv4 addresses, IPv6 networks, domains, sites), a per-site summary (15 rows plus "Other sites"), whether each list is printed, and, when either is over, the name and SHA-256 of the separate scope CSV. Templates print the totals and name that file instead of the list. The CSV (`report_scope.scope_csv`: deterministic, UTF-8 with BOM, formula-looking cells prefixed with an apostrophe) is served by `GET /client-reports/{id}/scope.csv` and the agent's `/assist/client-reports/{id}/scope.csv` from `ClientReportService.content()`: a draft's is built from its live scope; an issued report's is the file stored at issue (`freeze_report_scope` → `…/<report>/scope/scope.csv`; a report issued before the file was kept has it rebuilt from the frozen scope). The bytes are compared with the SHA-256 the report prints, and a download that does not match is refused — a logged 500 — rather than served as a different file. The summary's `scope_external` puts a "Scope file — send it with the report" section on the report page and a line in the issue dialog, a warning and never a block.
- **Queue metrics** — admin-only `GET /api/v1/system/queue-metrics` (`system_metrics.py` → `queue_metrics_service.py`) reports depth/in-flight/failure counts for **both** durable job queues (`ingestion_jobs` + `report_jobs`) so operators can see backlog and stuck work at a glance.
- **Parse errors** — `parse_errors` rows surface on the **Ingestion Results** page (Inventory hub, beside Scans; `/parse-errors` redirects there) with `user_message` strings tuned for operators, the format chain and the uninterpreted lines. Linked to `ingestion_jobs` via FK so the UI can show "this scan failed — see error #42".
- **Dead-letter columns** — `ingestion_jobs.retry_count` + `ingestion_jobs.last_error` surface in the `IngestionJobSchema` so the UI can highlight jobs that crashed repeatedly. `ingestion_jobs.skipped_count` + `parser_warnings` (v2.22.0) carry per-job parser quality stats (how many records were dropped, what malformed), persisted from `parser.last_parse_stats` after each successful parse.
- **Orphan reaping** — covered in §4; this is the recovery path when a worker segfaults or the container is killed mid-parse.
- **Version visibility** — `GET /` returns `{message, version, frontend_version, instance_id, cors_origins}` (the backend version is the `version` key), the user menu's **About BlueStick** item shows both (the bottom-right VersionFooter was retired by UX audit #12 and its component deleted in 5.247.0), and startup logs print them on every boot.

## 9. Extending the system

**Adding a new parser.**
1. Drop a file in `backend/app/parsers/{tool}_parser.py`. Inherit structure from an existing parser; use `parser_utils` for shared concerns (`ensure_scan`, `extract_first_ip`, `record_savepoint` around any record whose failure you catch and skip, `read_tool_text` for text that reaches a Text column). Accept `source_tool=` in `parse_file(**kwargs)`.
2. Add its `looks_like_*` sniffer to `content_detection.py`, its attempt to `ingestion_service._build_parsing_attempts` under the file type it serves (a try-anyway attempt wrapped in `_fallback`), its class to `build_parser_dispatch_map`, and its `file_type` to `format_registry.FORMATS`. Four tests pin this chain — `test_parser_dispatch_contract.py`, `test_ingestion_format_chain.py`, the content-detection module-surface test in `test_phase1_regressions.py`, and `test_parser_coverage.py`.
3. Describe what it reads in `app/data/parser_coverage.json` (the "What BlueStick reads" page) in the same commit; if the extension is new, update `ALLOWED_UPLOAD_EXTENSIONS`, `frontend/src/data/uploadFormats.ts` and `documentation/UPLOAD_FORMATS.md` together (test-pinned).
4. Add fixtures to `artifacts/` (or `backend/tests/fixtures/`) and a test in `backend/tests/` that runs the parser against the fixture and checks the canonical host/port shape.
5. If the parser touches XML: use `defusedxml` (as `nessus_parser.py`) or `xml_stream_helpers.iterparse_safe` (as the nmap, masscan and openvas parsers). Both defeat XXE; never reach for bare `xml.etree` or `lxml.etree`.

`documentation/PARSERS.md` has the full walkthrough.

**Adding a new agent workflow.**
1. Keys are not scoped any more (§2.2): every key belongs to one project session and carries its operator's project role. Decide instead which ROLE a call needs (reads: membership; bulk exports: `auditor`; writes: `analyst`) and what record the work leaves (a host test, an evidence record, a proposal, a note, an upload — each carries the session's id).
2. Add the endpoint to the right module under `backend/app/api/v1/endpoints/` (`agent_browse.py`, `host_tests.py`, `agent_proposals.py`, `agent_recon.py`, `agent_assist.py`, or a new one mounted under `/agent` in `api.py`). `enforce_agent_operator_access` is mounted on every agent router and applies the role floor; object-level rules (an upload belongs to its session; a host test or evidence record belongs to the key's project) stay in the handler or its service. A write that changes what the team concluded is a proposal (§5.7), not a direct route. A read whose page needs more than membership declares its floor on the route (`dependencies=[Depends(agent_read_floor(ProjectRole.AUDITOR))]`, never on `include_router`) and gets a row in `test_agent_role_route_matrix.py`. If it should be an MCP tool, add it to `mcp_tools.py` — description, method, path and any per-argument description; its parameters come from the route — the MCP layer makes no authorization decision; `test_mcp_enum_contract.py` and `test_agent_capabilities.py` (the exact list of gated agent write routes) must be updated with it.
3. Tag new agent-guide sections with the workflow name so they appear in the sliced response; update the prompt builder in `agent_prompt_service.py` if needed **and bump the prompt version** — set `PROMPT_VERSION` and rewrite `PROMPT_CHANGES` (what this version changed; earlier versions are in the changelog) in `agent_prompt_service.py` — so agents on the old prompt can detect they're stale.
4. Add contract tests to `backend/tests/` that exercise the new endpoint with a session key (`test_host_tests.py` shows the pattern). The agent API call log middleware will capture the new endpoint automatically — extend the `_collect_referenced_ids` helper if the call carries host/entry references the parser doesn't already pick up.

**Adding a new UI feature.**
1. Route pages belong in `frontend/src/pages/`; shared components in `frontend/src/components/`.
2. Reuse the per-domain typed clients in `services/api/` (import them through the `services/api` barrel, which tests mock) and the shared `uiStyles.ts` helpers. `uiStyles.ts` exports only `safeFallback` and `stickyBelowChrome`; truncation is Tailwind (`truncate`, `line-clamp-*`, `break-words`) composed with `cn()` (`utils/cn.ts`). There is no `sx` prop anywhere — that was MUI.
3. Test worst-case data (200-char hostname, long filename, null values, empty arrays) at desktop widths, including a narrowed window. Desktop-only product — no mobile layouts (UI_STYLE_GUIDE.md §3).
4. Before shipping: type check clean under strict mode, handle Pydantic 422 shapes in error paths.

**Adding a new service layer module.**
- Single responsibility per file. If a service commits internally, document the policy in the module docstring (see `integration_service.py`, `llm_provider_service.py`). If it defers commit to the caller, say so (see `host_test_service.py`, `agent_evidence_service.py`). Commit boundary ambiguity is an audit finding waiting to happen.

## 10. Test & quality gates

- **Backend** — `pytest` with a 68% coverage floor in `backend/pytest.ini` (the floor is a ratchet — raise it as coverage climbs). The suite has **~2,100 test functions** (more once parametrized) in ~245 modules (v2.427) across service, parser, and contract layers under `backend/tests/`. `conftest.py` uses the SQLAlchemy join-to-outer-transaction + nested savepoint pattern so services that commit internally (integration, LLM provider, agent API log middleware) don't break test isolation. **Postgres is the preferred test backend** — the harness auto-creates a `<app-db>_test` database on the app's own Postgres server when reachable, falling back to in-memory SQLite when not. The Postgres path lets the Postgres-only code (`pg_advisory_lock`, masscan batch-upserts, the raw `pg_catalog` SQL in `delete_scan`) actually run.
- **Frontend** — Vitest + Testing Library. Coverage spans page-level views (Hosts, Operations, ProjectActivity, AgentSessionDetail, the scan compare view), shared components (HostFilters, HostCommandBar, HostInspector, ProposeTestsDialog), and pure utilities (host query-DSL translation, tool-ready output, navigation manifest, version consistency).
- **No hosted CI — one local gate, `scripts/check.sh`** (`make check`; `--fast` skips the migration round trip). It runs the backend suite in the **report-worker** image with `report-templates/` mounted and fails if any test skipped for want of Quarto or the templates (in the plain `backend` image the client-report tests, the hostile-text contract among them, skip and the run is green), then `ruff check` in the same image (pyflakes rules only, `backend/ruff.toml`; any finding fails), then frontend `tsc --noEmit` + `npm run lint -- --max-warnings 0` (ESLint: the Rules of Hooks, effect dependencies, the `services/api` barrel import, one helper each for a file save and an absolute moment) + `vitest run`, then the Alembic round trip and `alembic check`; a one-screen summary, non-zero on any failure. The coverage floor in `backend/pytest.ini` is not enforced by any routine run (every recipe passes `--no-cov`). The GitHub Actions workflow was removed in 2026-09 (it had never run on this repository). The three gates, for running one alone: `scripts/test-alembic-roundtrip.sh` walks every migration down and back up against a throwaway Postgres; the backend suite plus `alembic check` (model/migration drift) run in a one-off container (recipe in CONTRIBUTING.md; drop `--no-cov` to check the 68% floor from `backend/pytest.ini`); the frontend runs `tsc --noEmit` → `npm run lint` → `vitest run` → `npm run build`.
- **Type safety** — frontend runs TypeScript strict mode with `noUnusedLocals` / `noUnusedParameters`, so an unused import fails `npm run build` (and the image build); every PR should typecheck clean before merge. Backend uses gradual typing via type hints but does not enforce mypy in CI.

## 11. Deployment

Single entry point: `./scripts/deploy.sh`. Options:

1. **Start / rebuild** — takes a pre-deploy backup (database and `uploads/`), snapshots the images, then in this order: **builds** (a failed build stops here, the old containers still running); **stops the two workers**; starts the **database and the backend alone**; **waits for the backend** (`DEPLOY_HEALTH_TIMEOUT`, default 1800 s — it serves only after `alembic upgrade head`), checking that the container answering is the image just built; then starts the **workers**; then `up -d` for everything, which starts the **frontend**. The backend goes alone so that one process migrates with nothing else connected (`scripts/stack-lib.sh`, shared with option 7 and `restore-db.sh`). A container that exited or keeps restarting is a failed boot (roll back, option 7); one still running at the timeout is a migration in progress (the script checks the migration advisory lock and says so) and must not be rolled back. The backend's Docker health start period is 15 minutes for the same reason. After a healthy start it lists data repairs not yet applied.
2. **First-time setup** — auto-detects host IP, generates `.env` from `.env.example`, generates SSL certs, then builds and starts all five containers with the same staged start as option 1 (backend alone, wait for it, workers, frontend) — it says so and exits non-zero when the build fails or the backend does not come up, instead of printing "setup complete". Creates a default `admin` user on first boot. The password is taken from `DEFAULT_ADMIN_PASSWORD` when that is set to something other than the literal `admin`; otherwise a cryptographically random URL-safe password is generated (v2.90.3), never logged (the boot log names the file), and written mode 0600 to `/app/uploads/initial-admin-password.txt`. `must_change_password=True` is set on the row so first login forces a rotation regardless of source.
3. **Reconfigure IP** — regenerates `.env` + SSL certs for a new host IP.
4. **Nuclear clean** — removes THIS Compose project's containers, volumes, networks and built images, selected only by the `com.docker.compose.project` label (never by a name substring: a second copy of the tree on the host is not touched), and this folder's `.env`. It first saves `.env` + `ssl/` (as option 6 does — the dump's encrypted secrets need the key in `.env`) and runs `backup-db.sh`; a failed backup stops it until a second typed confirmation. Destructive.
5. **Security status** — reports SSL state and whether the database port is exposed.
6. **Back up `.env` + SSL** — copies them to the parent folder.
7. **Roll back** — returns to the previous build, in this order: re-points the image names at the `bluestick-rollback-<service>:previous` snapshot; **stops the application** (the database stays up); compares the database's schema revision with `PREDEPLOY_ALEMBIC_REVISION` recorded at the pre-deploy backup. Unchanged → no restore (a failed upgrade normally rolls back to where it started). Changed, or not determinable → the previous build cannot start on that schema, so it **restores the pre-deploy dump first** (`restore-db.sh --yes --no-start`; asks, default yes; declining leaves the instance stopped unless `START ANYWAY` is typed). Only then the staged start, with `--no-build`, and a closing line with the state the instance is in and the next step.

Auxiliary scripts (`scripts/README.md` has the full list):

- `scripts/collect-logs.sh` — anonymised diagnostics bundle (with `scripts/scrub_logs.py`).
- `scripts/backup-db.sh` / `restore-db.sh` — database (+ `uploads/`) backup and restore. A backup is read to its END before it counts — a dump is converted back to SQL and discarded (`pg_restore -f /dev/null`; listing it proves nothing, the table of contents is at the front of the file), each tar is listed to its end — and its size and SHA-256 go in the `.meta` beside it. It is written 0600 in a 0700 directory, fails when the uploads archive fails (`--allow-missing-uploads` to accept), and the newest `BACKUP_KEEP` are kept. A restore compares the file with its `.meta` (size, SHA-256) and reads a dump to its end before it drops anything (`--force-unverified` to override), takes a safety backup first, and starts the stack staged. Both run `tar` in the database's own image — nothing is pulled.
- `scripts/check.sh` — the gate (see §10). `scripts/data_repairs.py` — the data-repair ledger (see §8).
- `scripts/upgrade-instance.sh` — carry a running instance's local state into a freshly copied source tree, then deploy.
- `scripts/status.sh` — container status, the newest backup's age, data repairs not yet applied.
- `scripts/generate-ssl-cert.sh` / `generate-ssl-cert-simple.sh` — SSL certificate helpers (also invoked by `deploy.sh` during first-time setup).

**Scaling.** The stateless backend and frontend containers can run multiple replicas; the ingestion and report workers are each currently a single long-lived process and should not be replicated as-is (the `FOR UPDATE SKIP LOCKED` claim is safe for multiple workers, but the orphan-reaper logic assumes one reaper per queue). Postgres needs external strategies (managed service, read replicas) for anything beyond single-host deployments. There is no general job scheduler: beyond the two workers' periodic callbacks (the ingestion worker's reaper, backlog check and webhook sweep), the API runs two background loops — the hourly expired-session cleanup, which also ends agent sessions whose keys have expired past their renewal window (`lapse_expired_agent_sessions`), and agent-API-call / audit-log retention (`startup.py`); re-correlation and vuln refresh remain on-demand.
